1 · PLAYBACK

What I understood

  • The admin works and the business rules stay. The job is fewer clicks, one way to save, and no lost input.
  • Maria is the main user. At a 1360 px laptop she handles money, courses, content and newsletters. On a phone or tablet she handles the course day, registrations, students and assessing practical photos. She is often away from the desk, so the phone matters for daily work, not for the site editors.
  • Today there are five save models side by side (obs. 1, G4). Only the protocol screen works the way the whole admin should (obs. 14). Its autosave engine (protocol-autosave.ts) becomes the base for every form.
  • Explicit buttons remain only for actions that leave the admin (mail, protocol, assessment, invoice, contract, newsletter) and for anything that cannot be undone.
  • The work has to fit the existing app: server-rendered pages, CSS modules, drawers opened by a URL parameter, 44 px targets, old Safari. The look is refined, not rebranded.
  • Wherever a better flow needs the server to behave differently, it goes on a separate behaviour-change list for you to decide.
QUESTIONS THAT CHANGE THE DESIGN

I'm continuing with the default shown for each one. Every default marked My call is easy to change later.

Q1
Do autosaved edits on published content go live at once?Today a course or home-page edit goes public when she presses „Salvesta“. With autosave, the text would appear on the site about 1.5 s after she stops typing. The alternative is a draft layer with an „Avalda muudatused“ button, which is a second save model.Decided: draft layer. On published content, autosave writes a draft; the header shows „Avaldamata muudatused: {n}“ with „Eelvaade ↗“ and the explicit „Avalda muudatused“. Unpublished items save straight to the record.
Q2
Is money received autosaved or explicit?The figure in „Laekunud summa“ can confirm or un-confirm a place (obs. 4). Saving it as she types could flip a status halfway through a number.Decided: explicit. Money is recorded as a payment with one button („Lisa laekumine“), which adds to the total and checks seats. This merges the two money paths and is listed as a behaviour change.
Q3
Which tablet is used on the course day, and how is it held?At 641–900 px the current layout uses a narrow 190 px sidebar, which leaves little room for the protocol on an iPad held upright (834 px).Decided: below 900 px the phone top bar is used. The sidebar starts at 900 px.
Q4
Who writes the Russian, and when?If it happens in a separate pass, possibly by someone else, the design should favour a side-by-side view. If Maria writes both languages as she goes, an inline switch is enough.Decided: Maria writes both as she goes. One page switch with ET and RU; no side-by-side mode.
Q5
Should „Testimine“ appear in Maria's menu?Today the overview card is its only entry point, and the card disappears once nothing is open (obs. 7).Decided: yes, last in the „Haldus“ group for every admin. Its badge counts only the signed-in person's open checks.

3.1 · SAVING (G4, G5, OBS. 1)

Everything saves itself, and one status line per screen says so

The protocol engine is generalised into useAutosave, and every editor and drawer uses it. A field saves 1.5 s after typing stops, on blur, when the tab is hidden, and before leaving the page. Choices, toggles, reordering and uploads save at the moment of the tap. A local copy is kept until the server confirms, and edits from two devices are caught by the same version check the protocols use today.

3.2 · DRAWERS AND UNSAVED INPUT (G6, OBS. 2)

Closing a drawer never loses anything

Drawers stay what they are today: Drawer.tsx, opened by a URL parameter, 560 px wide, full screen on a phone. Because they now autosave, closing them with ✕, Esc or the backdrop is safe. The only time closing has to wait is when something isn't confirmed yet.

Everything savedCloses at once. Focus returns to the row, as today.
Save in flight or waitingThe pending save is sent first and the drawer closes when it's confirmed, usually in under a second. Nothing is asked.
Can't save (offline, error, invalid field)An in-place question appears at the top of the drawer: what isn't saved and why. „Jää siia“ is the primary button and returns focus to the field. „Sulge, tekst jääb seadmesse“ keeps the local copy and restores it the next time the drawer opens.
An upload is still runningSame question; the upload carries on while she stays.

Navigating within the admin (sidebar, links, Back) uses the same guard through one useLeaveGuard hook in Shell. That covers the parked "unsaved warning on in-admin navigation" item. The browser's own prompt (beforeunload) stays only for closing a tab while text is unconfirmed.

Drawers that only show information (feedback answers) have no status line. The scroll lock gets scrollbar-gutter: stable, which closes the parked layout-shift item on Windows.

3.3 · CONFIRMATIONS (G8, OBS. 5, 13)

One ConfirmPanel, one rule, one set of words

Patterns A, B and C (G8) become one component, ConfirmPanel. It opens in place of the button that triggered it and takes focus. It states the question and lists the consequences in plain lines: who gets mail, what changes in public, and what can't be undone. The "yes" button repeats the action and its count, so it reads as a sentence. „Katkesta“ returns focus to the trigger.

When a confirmation is needed
ConfirmPanelThe action can't be undone, or it mails more than one person, or it changes what a student has right away (access, seat, test). Examples: „Kustuta …“, „Lukusta ja saada kõik“, „Saada kõigile“, „Tühista registreerimine“, „Tühista arve“, „Võta tasumine tagasi“, „Lõpeta ligipääs“, „Peata saatmine“, and saving a changed e-course contract that makes students re-accept. Informed buttonA send to one person, with the summary written on the button itself: one tap, nothing hidden. Examples: „Saada protokoll Eliisele“, „Saada hinnang · 3 kinnitatud, 1 paranda“, „Saada test tagasi · 1 vale“. The protocol send and the test-review send now behave the same way (obs. 5, 13). UndoBarA reversible one-tap action: remove an image, file or list row, hide or publish a review, mark a request done. Shows „{Mis juhtus}. Võta tagasi“ for 8 s. Refuse earlyAn action that isn't possible isn't offered, and the reason is shown where the button would be. For example, a booked session shows „Toimumisel on registreeringuid — märgi see „Tühistatud“.“ in place of „Kustuta toimumine“, so she doesn't need three taps to find out (appendix 03).

3.4 · ET/RU EDITING (G7, OBS. 10)

One language switch per page

The ET/RU pills on each field are removed. A single LangSwitch in the page header sets the content language for every I18nInput on the page, through context. ET is the default, and the choice is remembered per device. Maria writes both languages as she goes (Q4), so two modes are enough.

• In RU mode, each field shows its Estonian text in grey above the input, so there is no switching back to check. • An empty RU field keeps the „tõlge tulekul“ tag and offers „Kopeeri eesti keelest“ (a 44 px link) to start from the Estonian. • The switch counts untranslated fields: „RU puudub 3 väljal“, with „Järgmine →“ to jump to the next one. • The rules stay the same: ET is required when RU is filled, and the error text is unchanged. • Admin labels are always Estonian. Only the content switches.

Clicks for a Russian pass over a course with 12 bilingual fields: 12 → 1 (one tap on RU), plus one tap per „Järgmine“ if she uses it.

3.6 · ONE WORD PER ACTION (OBS. 11)

A short glossary, applied everywhere

The main rule is that „Tühista“ is only ever a business action: cancelling a registration, an invoice or a session. Stepping out of a form or a question is always „Katkesta“. That keeps „Tühista“ from meaning "never mind" on one screen and "cancel the invoice" on the next.
