# MS LAB — how the site is hosted and deployed

Since 08.10.2026 the site is **https://mslab.ee**, on **Vercel**, on Maria's accounts (from 03.10 to 08.10.2026 it was https://mslab.diipsolutions.eu on Dim's, which now only redirects to mslab.ee). The Cloudflare Workers that served it before (`mslab-web`, the app, and `mslab-guide`, the old design hub) are retired and deleted; nothing in the repository deploys them any more. This file is the current setup. It holds variable **names** only: values are never written in the repository (it is public), and the secrets are entered by Dim himself in the Vercel dashboard.

## 2. Environment variables

Set in the Vercel project: Settings → Environment Variables (or `vercel env add <NAME> production`). A change reaches a deployment only when a **new** deployment is made. The build needs none of them: no page is prerendered from the database (`[locale]/layout.tsx` returns no static params on purpose; pages are rendered on the first request and then cached), and the start-up check runs when the server starts, not during the build, so `next build` succeeds with an empty environment. They are read at run time. Without a required variable every request answers 500 with an error that names the variable, never its value (`src/instrumentation.ts`, `src/server/env.ts`).

Every variable on Maria's Vercel project is a **plain** variable, the secrets too: that is the owner's choice (08.10.2026), so nothing is marked "Sensitive" there. "Secret" below means that the value never goes into the repository, a log or a message. To add a variable again (a new value), keep it plain too: `vercel env add <NAME> production --no-sensitive --force` (the CLI asks for the value; it is never typed into a file).

## 3. Deploying

**Normal way (once the branch is merged into `main`).** The project's Git integration (`mslabinformation-collab/mslab`) deploys `main` to production on every push, and any other branch or pull request to a preview URL (`*.vercel.app`, noindex like everything else). Nothing else is needed: the build is `next build` in `app/`. Database migrations are not part of it (section 6): apply a new one **before** the code that needs it goes live.

**Previews.** A preview deployment builds, but no Preview environment variables are set (section 2), so the start-up check fails and every page and API request answers **500** (static files under `app/public`, such as `/guide/`, may still load). That is harmless: it touches no database and is behind Deployment Protection. Do not "fix" it by enabling the production variables for Preview. If a working preview is ever wanted, give Preview its own database and variables.

**After the first Git deploy of `main`.** That build puts live the R2 request handling and logging written after the CLI deploy of 03.10.2026, so check these once (replace the host if it has changed):

1. A key that does not exist answers 404 within a second: `curl -s -o /dev/null -w '%{http_code} %{time_total}s\n' https://mslab.ee/media/img/00000000-0000-4000-8000-000000000000.jpg`. A request that hangs means the R2 call is stuck (see the canary in `app/tests/unit/r2.test.ts`).
2. An image that exists (take an `/media/img/…` address from a course page) answers 200 with `cache-control: public, max-age=31536000, immutable`. Ask twice with `curl -sI`: `x-vercel-cache` is `MISS`, then `HIT`. The app also sends `Vercel-CDN-Cache-Control` so that the CDN keeps the image, but Vercel strips that header from the answer, so the `HIT` is the evidence.
3. One admin upload: sign in at `/admin`, upload a small image in a picture field (the upload route answers 201) and open its `/media/img/…` address. Uploads are never deleted today, so use a small image.
4. One manual cron run: Settings → Cron Jobs → Run on `/api/cron/sweep` answers 200, and the runtime log shows `[cron] sweep: N expired kv entries, N login codes, N sessions, N mail counters, N stuck video uploads deleted, N stuck processing videos found ready, N marked failed, N video rows left for the next run`.
5. Then the read-only checks at the end of this section.

**Manual fallback (the Vercel CLI).** The CLI reads the `.vercelignore` of the folder it runs in, so it works from the **repository root**, where the root `.vercelignore` is applied (an `app/.vercelignore` is not read there, and a deploy from `app/` is refused: the project's Root Directory `app` would become `app/app`). The root file is an allow-list of what `next build` in `app/` reads: `app/src`, `app/public`, `app/drizzle` and six files (`package.json`, `package-lock.json`, `next.config.ts`, `tsconfig.json`, `vercel.json`, `drizzle.config.ts`), about 450 files and 42 MB in October 2026. Everything else stays out, whatever lies around locally: `.wrangler`, `.open-next`, `.next`, `node_modules`, `.env*`, `.dev.vars*`, `.media-local`, test output and everything outside `app/` (`app/tests/unit/vercelignore.test.ts` guards this). It uploads the working tree, though, so uncommitted edits go up too. For a production deploy that is exactly the commit, deploy a clean copy of what is committed:

```
mkdir <scratch>
git archive HEAD app | tar -x -C <scratch>
mkdir <scratch>/.vercel && cp .vercel/project.json <scratch>/.vercel/
cd <scratch> && vercel deploy --prod
```

`.vercel/project.json` links the folder to the project (it is git-ignored; `vercel link` makes it). The CLI must be signed in to Maria's team `ms-lab`: Dim keeps that login in a global config folder of its own (`vercel --global-config ~/.vercel-mslabinformation …`). The CLI prints the deployment URL; the production alias moves to it when it is ready. `vercel rollback` or the dashboard (Deployments → a good one → Promote to Production) goes back to an earlier deployment.

After a deployment, check it read-only: `node tools/cache-smoke.mjs [base] [--only=A,B,C]` (A and B: 90 GET/HEAD requests over the main pages, the hub and a prototype, exit 1 on any answer that is not 2xx or 3xx, the `x-vercel-cache` counts printed; C: the client account's shells come from the cache without `set-cookie`, `/api/konto/me` answers 401 `private, no-store` and is never cached, a query on a shell gets a 303 into the fragment), and `E2E_BASE_URL=<site> E2E_ALLOW_REMOTE=1 npx playwright test headers --project=chromium` (from `app/`) for the headers. A run against a deployment is read-only: the form tests skip themselves and every POST is blocked.

## 5. The daily cron

`app/vercel.json` has one cron: `GET /api/cron/sweep` at 03:00 UTC every day (the Hobby plan allows daily crons only; the exact minute within the hour varies). It deletes the expired `kv_entries` rows (the rate-limit counters, which hold visitors' addresses, are gone a day after their window at the latest even when nobody submits a form), the expired client login codes (they hold the address), client sessions ended or expired more than 30 days ago, and daily mail counters older than 7 days. With online payments set up (section 11) it also asks Montonio (`GET /orders/:uuid`) about every pending payment that has an order and is older than 45 minutes and younger than 14 days (oldest first, at most 50 a run, and no new question after the same 35 seconds of the run; one begun has Montonio's 15 s) and settles what Montonio says, through the one door every paid path ends in (`settlePayment`). Pending payments of 14 days, and those whose order was never created (no Montonio order 45 minutes after the start), become failed (at most 50 a run, oldest first; a prepayment's seat hold ends with it). When unpaid seat holds ended in the last day, or a payment the check failed freed one, the calendar and the course pages are revalidated. A payment that cannot be settled (a settlement, or a stale row, that throws) is counted as an error and logged by its id and the error's class and code only: the run goes on with the next payment. Each of the two loops (the stale rows, the asking) stops early only on connection errors: after 3 of them in a row (`MAX_CONSECUTIVE_ERRORS` in `app/src/db/queries/payments.ts`; SQLSTATE class 08, the database shutting down, starting up or full — 57P01, 57P02, 57P03, 53300, as in a Railway restart — or the driver's own connection errors) the rest waits for the next day; any other error is that payment's own, and the loop goes on within its 50 rows (and, for the asking, its 35 seconds). When Montonio says a payment is PAID but the app cannot settle it (not a transient or connection error, which the next run gets past), Maria is alerted once: "Makse vajab kontrolli: {nimi}" (by mail and Telegram, remembered for 30 days in the KV as `pay:stuck:<id>`); she records it by hand (at the registration; an e-course, which has no registration, she opens under Õpilased). A payment the webhook or the return records before that alert goes out gets no alert, and so no follow-up. Should the app record that payment after all (the webhook's retry, the return, or a later run, once the fault is gone), Maria gets one follow-up, "Makse on nüüd kirja pandud: {nimi}", which asks her to remove a sum she added by hand at the registration so it is not counted twice (an e-course opened by hand needs nothing), and `pay:stuck:<id>` is removed. A payment Montonio does not answer for is only counted ("not answered") and asked about again the next day. The check asks about pending payments only: a refund made later reaches the app through Montonio's notice (section 11, item 5), never through the daily check. With Bunny set up (section 10) it also gives up lesson videos left unfinished for a day, at most 20 of each kind a run, and no new video is started after 35 seconds of the run (a video begun is finished, which takes about 20 seconds at most, so the run stays under `maxDuration`; the rest wait for the next day, and the log says how many). Hobby's functions may run up to 300 s: the route's `maxDuration = 60` is our own guard. An upload still `uploading` 24 hours after it began is asked about at Bunny and, if it never arrived, given up (the lesson gets its replaced video back, or has none, and only after that write is the video deleted from Bunny); a video still `processing` 24 hours after its upload began is asked about, kept if Bunny says ready, and otherwise marked failed, so the admin shows "Töötlemine ebaõnnestus" with "Lae uuesti üles". A ready video is never touched, and a replaced video that still plays is deleted only once the new one is ready. Vercel sends `Authorization: Bearer <CRON_SECRET>`; with no `CRON_SECRET` set, or any other header, the route answers 401. Crons run on the production deployment only. Check it under Settings → Cron Jobs (a run can be started there) and in the runtime logs: `[cron] sweep: N expired kv entries, N login codes, N sessions, N mail counters, N stuck video uploads deleted, N stuck processing videos found ready, N marked failed, N video rows left for the next run` (counts only: no video ids, no addresses), and, when the 35 seconds ran out, `[cron] sweep: no new video row started after 35 s`. With online payments set up the log adds a second line, `[cron] sweep: payments N checked at Montonio, N settled, N not answered, N failed as stale, N left for the next run, N seat holds ended, N errors` (counts only: "settled" are the payments whose status changed, "failed as stale" the 14-day-old and never-created ones), and `[cron] sweep: no new payment asked about after 35 s` when the time ran out; without online payments there is no payments line at all. N errors above 0 counts the payments the app could not settle, or could not fail as stale: they stay pending, the line `[payments] a payment could not be settled (payment N): <error class>` names each by id, and the next day's run tries them again (look at them in Maksed → Pooleli). The 200 answer is JSON of counts: `ok`, `deleted`, `logins`, `sessions`, `mailDays`, `uploads`, `processingReady`, `processingFailed`, `videosLeft` and, for the payments, `paymentsChecked`, `paymentsSettled`, `paymentsExpired` (failed as stale), `paymentsLeft` and `paymentsErrors` (all 0 without online payments); a database failure is a 500 `{ ok: false }`. A Bunny failure on the status read of one video is logged as `[video] stuck … not swept: <error class>` and only then is the video tried again the next day. When the Bunny delete fails after the lesson's row was already reset, the row is not tried again: the log says `[lesson] video not deleted: <error class>` (no id) and the empty video stays in Bunny. Compare Bunny's library list with the lessons now and then, and delete what no lesson uses.

## 6. Migrations on Railway

The SQL files are in `app/drizzle/` (additive: no migration drops or rewrites data). Vercel does not run them. To apply the pending ones to the Railway database, from `app/`:

```
DATABASE_URL='postgres://…@<host>.proxy.rlwy.net:<port>/railway?sslmode=require' npm run db:migrate
```

- Take the **public** TCP proxy URL from the Postgres service of Maria's Railway project `mslab` (Connect → Public Network) and add `?sslmode=require`. Put it in the shell only: never in a file, never in the repository (`.env*` files are git-ignored, but an `.env` that a local `next dev` reads would then point the dev server at production data too).
- `drizzle-kit migrate` applies what is not yet recorded in its own table, in order. Check afterwards (`select count(*) from drizzle.__drizzle_migrations`; 7 after phase 2b's 0006).
- A new migration: change `src/db/schema.ts`, `npm run db:generate`, review and commit the SQL. Railway runs Postgres 18 (`ALTER TYPE … ADD VALUE` needs 12 or later).
- Order: migrate first, then deploy. An additive migration is harmless to the code that is live, so a rollback of the code (section 8) stays safe.

## 7. The database tools and their guards

All take the connection URL from `DATABASE_URL` in the shell and print counts only: never the URL, a key, a value or an address. Each says which database it means with `--target`, and refuses when the URL disagrees: `local` only for `localhost`, `127.0.0.1` or `::1`; `railway` only for a host ending in `.rlwy.net`, `.railway.app` or `.railway.internal` (`src/db/fill-ru.ts` `targetMatches`).

| Tool | What it does | Guards |
|---|---|---|
| `npm run db:seed -- [--target local\|railway] [--reset [--force]]` | Inserts the prototype content that is missing; existing rows are untouched. | Without `--target` it works on a local database only. `--reset` (deletes the content and the registrations) needs `--target`, and `--force` when registrations would be deleted. `--reset` also refuses, and `--force` does not help, while any lesson progress, course access, lesson video or lesson file exists: the cascade would delete the students' progress and access, and the Bunny videos and R2 files would stay behind with nobody able to delete them. The message (counts only) says what to do: remove lesson videos and files in the admin first; progress or access means this database has real students, so do not reset it and use a fresh database for a clean seed. |
| `npm run db:demo -- --target railway\|local [--apply \| --remove]` | The removable sample registrations, requests and subscribers that make the admin look lived in. | `--target` is required. A dry run unless `--apply` or `--remove` is given. |
| `npm run db:copy-kv -- --target railway\|local --file <export.json> [--apply]` | The one-time copy of the review comments (`fb:*`, their `id:*` lookups and `tg:chat`) from the old Cloudflare KV namespace into `kv_entries`. The input is the namespace exported with `wrangler kv`: a JSON array of `{ name, value, expiration? }`. Rate-limit keys (`rl:*`) are never copied. | `--target` and `--file` are required. A dry run unless `--apply`; the apply is one transaction and idempotent (a second run changes nothing). The export holds the client's own text: keep it outside the repository and delete it after use. Done at the cutover (56 comments); kept for the record: the Cloudflare KV namespace was deleted on 08.10.2026, so it is not needed again. |
| `npx tsx src/db/fill-ru.ts --target railway\|local [--apply]` | Fills empty Russian sample texts of a database seeded before them. | `--target` is required; a dry run unless `--apply`. |

The test suites and the e2e run never write to Railway: they use PGlite and a local Postgres, and the e2e run refuses to start when any database setting points anywhere but this machine (`app/tests/e2e/local-db.ts`).

## 8. Rollback

1. **The code only.** Promote an earlier deployment (section 3). The database stays as it is; migrations are additive, so older code still runs. Before rolling back past phase 2c, set Hüpikaken (the admin page) to Kampaania or Väljas: the old admin cannot switch the newsletter popup row off, and the `campaign_one_active` index would refuse turning the campaign on while that row is active.

## 9. Hobby-plan limits to keep in mind

- 1 million function invocations a month and 100 GB of data transfer; an image is cached by Vercel's CDN (`Vercel-CDN-Cache-Control` on `/media`), the public pages by ISR.
- 4.5 MB request body: the upload limit in the app is 4 MB (the admin's browser shrinks images first).
- Cron jobs: once a day at most.
- A function that hangs would run for the plan's default 300 s: `/media` and the upload route set `maxDuration = 30`, and R2 gets 10 s to answer. The same holds for Bunny's API (10 s an answer; the account API and the webhook set 30). The daily cron sets 60 as its own guard (Hobby allows up to 300 s): at most 20 video rows of each kind, and no new one after 35 s of the run (a row begun takes about 20 s at most to finish: 35 + 20 is under 60); its payments check keeps to the same 35 s (a question to Montonio begun takes 15 s at most, and at most 50 are asked a run). Montonio has 15 s to answer (`REQUEST_TIMEOUT_MS`); the webhook, the return, `/maksa/<token>`, `/api/konto` and the two pages whose forms start a payment (the course page, for the registration's prepayment, and the e-course cart) set `maxDuration = 30`. Online payments add no polling: a payment costs a few calls (its start, Montonio's webhook, the return), and Montonio retries a webhook over 48 hours until it gets a 200 or 201, so only a failing app costs more.
- A student watching a lesson posts her progress about every 15 s (about 240 function calls an hour of video); 500 hours watched a month is about 120 000 calls.

## 10. Bunny Stream (lesson videos)

The lessons' videos live in one Bunny Stream library. Maria's browser sends a video straight to Bunny (a resumable tus upload that the server signs; nothing passes through Vercel), Bunny encodes it, and students watch it in Bunny's player inside the lesson page, through an address the server signs for four hours. These steps are for Dim. The names below come from bunny.net/docs as read on 06.10.2026 and from the names of the library's API fields; the dashboard may word them a little differently, so **confirm each label on the first setup and correct this section where it differs**.

1. **Create the library.** Done on 08.10.2026 on Maria's Bunny account: the library `mslab`, id 773592 (the value of `BUNNY_LIBRARY_ID`). For a new library: bunny.net → Delivery → Stream → **Add Video Library**. Name it `mslab`. Pick a storage region in Europe. Bunny's quickstart advises two or more regions for durability; every extra region keeps another copy (the screen shows the price). A lost video can be uploaded again from Maria's own file, so start with no extra replication (Dim's choice).
2. **The two ids.** The library's **API** page: the **Video Library ID** → `BUNNY_LIBRARY_ID`; the **API Key** → `BUNNY_API_KEY`. Take the library's own key: not the read-only key next to it, and not the account key of bunny.net's account settings (the app sends the library key as `AccessKey`).
3. **Security** (the library's security settings; the API field of each is in brackets):
   - **Embed view token authentication** ON (`PlayerTokenAuthenticationEnabled`). Its key (the docs call it the token security key) → `BUNNY_TOKEN_KEY`. The app signs each address as `SHA256_HEX(key + video id + expiry)`, as Bunny's docs describe. **CDN token authentication** is a different setting (it protects the video files themselves): leave it as it is, the player in the iframe uses the embed token.
   - **Allowed domains** (`AllowedReferrers`): `mslab.ee` and `www.mslab.ee` (and the project's own `*.vercel.app` address while testing).
   - **Block direct URL file access** ON (probably `BlockNoneReferrer`: requests without a referrer are refused). The lesson page sends the site's origin as the referrer to the player (`Referrer-Policy: strict-origin-when-cross-origin`), so playback is not affected. If the player stays blank after this is switched on, this switch is the first suspect.
   - **MP4 fallback** OFF (`EnableMP4Fallback`), so there is no downloadable MP4.
   - **Direct play** OFF (`AllowDirectPlay`).
   - Leave **early play** (`AllowEarlyPlay`), JIT encoding and DRM off: the app treats a video as ready at status 4 (Finished).
4. **Player controls.** In the library's player settings the controls shown are a list (the API field `Controls`: `play-large, play, progress, current-time, mute, volume, captions, settings, pip, airplay, fullscreen`). Try taking **fullscreen** and **pip** (picture in picture) out of it (to confirm on the first setup: that the dashboard offers this list, and that the player really drops those two buttons). The lesson page has its own "Täisekraan", which keeps the watermark with the address in view; Bunny's own fullscreen button does nothing useful inside the page's frame, and picture in picture shows the video with no watermark. AirPlay hands the picture to another screen the same way: leave it out too. A list to try: `play-large,play,progress,current-time,mute,volume,settings`. Playback speeds: at most 2× (the speed menu's list): the server's progress clock assumes 2× is the top speed (phase 2c, `TOP_SPEED` in `app/src/domain/lessons.ts`).
5. **Webhook.** In the library's settings, the webhook URL (`WebhookUrl`): `https://mslab.ee/api/bunny/webhook?secret=<BUNNY_WEBHOOK_SECRET>`. The secret is a long random string you make up (`openssl rand -hex 32`). The URL with its secret ends up in Vercel's request logs (accepted: it only lets someone ask the app to re-read a video's status). The webhook is a trigger and nothing more: the app reads the video's status from Bunny's API and never believes the body. Bunny also signs its webhooks (headers `X-BunnyStream-Signature` and friends, HMAC-SHA256 with the library's read-only API key); the app does not check that, it relies on the URL secret and on the re-read. Without a secret the app takes any call (still only a trigger), so set it.
6. **Vercel variables.** Settings → Environment Variables → **Production** (the API key, the token key and the webhook secret are secret but plain variables, the owner's choice; the library id is not a secret; never `BUNNY_FAKE_URL`); they reach the site with the next deployment:

   | Variable | Where it comes from |
   |---|---|
   | `BUNNY_LIBRARY_ID` | The library's API page: Video Library ID (step 2). |
   | `BUNNY_API_KEY` | The library's API page: API Key (step 2). |
   | `BUNNY_TOKEN_KEY` | The library's security settings: the embed view token authentication key (step 3). |
   | `BUNNY_WEBHOOK_SECRET` | Optional, from nowhere: the random string of step 5. |

   `vercel env ls production` lists the names without values.
7. **Check after the deployment:** admin → an e-course → a lesson → the video field offers "Vali video" (not "Video seadistamata").

**What the app uses.** The API `https://video.bunnycdn.com/library/<id>/videos`, tus `https://video.bunnycdn.com/tusupload` (straight from Maria's browser) and the player `https://player.mediadelivery.net/embed/<id>/<video>?token=…&expires=…`. The library's CDN hostname is not needed (no thumbnails or direct files in this phase). An unfinished upload is looked after by the daily cron (section 5).

**Keep the R2 bucket private.** The bucket `mslab-media` holds the public images under `img/` **and** the private lesson files under `lessons/`. The images are served by the app (`/media/img/…`) and the lesson files only through a short-lived signed address after the access checks; `/media` refuses `lessons/` keys. So **never attach a public custom domain to the bucket and never turn on its public `r2.dev` address**: every lesson file would then be open to anyone who learns a key. If images are ever to be served straight from R2, move them to a bucket of their own first.

**Costs.** Pay-as-you-go: about €5–15 a month at about 500 hours (the spec's estimate). Look at Bunny's bill after the first month (`docs/launch-checklist.md` section 8).

**Maria's Bunny account.** The library has been Maria's from the start (08.10.2026): nothing to move.

**First-use checks** (once, with the first real uploads; none of them can be done by a test, because the tests use a fake Bunny):

## 11. Montonio (online payments)

Students pay through Maria's Montonio store (phase 2b, spec `docs/superpowers/specs/2026-10-09-phase2b-montonio-payments-design.md`): bank links, and cards, Apple Pay and Google Pay when Maria turns them on in the store. The bank or the card is chosen on Montonio's own page; the site shows no bank logos.

1. **Keys.** Partner System → Business settings → Stores → (the store) → API Keys: the access key and the secret key, separately for the sandbox and for production (the live keys appear on that page once the store is activated; Montonio's help centre, "How to Find API Keys for Sandbox Payments"). Set `MONTONIO_ENV`, `MONTONIO_ACCESS_KEY` and `MONTONIO_SECRET_KEY` in Production as plain variables (`vercel env add <NAME> production --no-sensitive --force`; the CLI asks for the value, it is never typed into a file), then redeploy. `vercel env ls production` lists the names without values.
2. **Nothing to set in Montonio for the way back.** Every order carries its own `returnUrl` (`/api/payments/return`) and `notificationUrl` (`/api/payments/notify`). The `returnUrl` is on the address the payment was started from when that is one of the site's own (among them mslab.ee, www.mslab.ee and the deployment's own Vercel addresses: `linkOrigins` in `app/src/server/site.ts`), else on `SITE_URL`. The `notificationUrl` is always on `SITE_URL`, never on the request's address: Montonio calls it from outside, for up to 48 hours. The webhook must reach the app while the coming-soon gate is on: `/api/payments/notify` always goes through it, and so does `/maksa/<token>` (the mail's "Maksa" link); the return and `/makse` are behind the gate like the rest of the site (admins with the preview cookie).
3. **What the app sends.** `payment.method` `paymentInitiation` with no preferred bank, `paymentDescription` `MS LAB MSLAB-M<id>`, never a `paymentReference`; every new attempt is a new order with a new `merchantReference` (`MSLAB-M<id>`, the row of the `payments` table; `MSLAB-M` is production's prefix, item 6). Pressing "Maksa" / "Proovi uuesti" again while that attempt's order is open (30 minutes from its last sending; the same amount) sends the same order again under the same reference: Montonio replaces the unpaid order, so a payer never has two orders to pay. When Montonio refuses that re-send or does not answer it (the order may be paid already, its notice late), the payer is told "Midagi läks valesti", but the payment stays pending with its seat hold and the next press sends the same reference again; only a first sending that gets no order fails its payment. Should two payments of one registration be paid all the same, so that the sum is over the course's price, Maria gets "Ülemakse: {nimi}, {kursus}" and refunds the part over the price in Montonio. At most 5 new attempts a registration an hour and 5 starts from one IP address in 10 minutes (`PAY_STARTS_PER_IP`; the `/maksa` page and the account share that counter); more is refused ("Liiga palju katseid …"). The app sends no `expiresIn`, so Montonio's payment window is its default 30 minutes, and an unpaid group registration holds its seat as long (`SEAT_HOLD_MS` in `app/src/domain/sessions.ts`, which the re-send window uses too): if an `expiresIn` is ever sent, change `SEAT_HOLD_MS` with it.
   - **A group registration** is stored at once with its seat held and the prepayment starts; the answer carries Montonio's page. If Montonio does not open the order, the registration stands, the hold ends, and "Maksa" is offered later (the mail's `/maksa/<token>` page, which only shows the amount until its button is pressed, so a mail scanner creates no order; and Minu koolitused). Maria's bank transfer stays the second way under "Maksa".
   - **An e-course** has no account and no access before the payment. A paid purchase opens the access by "payment" (shown as "veebimakse" in Õpilased) and mails the payer a login. Buying again never shortens access: the end date is the later of the current one and today plus the course's months. The same address cannot pay the same e-course again for 30 minutes after a paid or held purchase (held: Montonio says paid but the amount did not match, and Maria is checking it; the cart says "Makse on juba tehtud — vaata oma e-posti."). If the access cannot be opened (the course is gone, or the grant is refused or fails), the payment still counts and Maria is told ("E-koolitust ei avatud …"). A transient database error rolls the whole settlement back; Montonio's retry, the return or the daily check settles it later. If Montonio does not open the payment at all, the cart says "Makse ei avanenud. Jäta oma e-post, anname teada." above its purchase-interest form.
4. **What the app trusts.** Only an order token (or a refund notice's token, item 5) signed with the store's secret key (HS256); one that cannot be verified is a 400 to the webhook (Montonio retries) and "katkestatud" at the return. A token for another store, for another order, or past its own expiry (`exp` and 60 seconds' grace; a late retry) is confirmed with `GET /orders/:uuid` before anything changes (no answer from Montonio: the webhook answers 503 and Montonio retries). A paid amount or currency that is not the payment's makes the payment `held` ("Ootel kontrollil" in Maksed): nothing is confirmed or opened, and Maria gets "Kontrolli Montonios". Paid is a floor: a later ABANDONED or FAILED changes nothing. Three things happen after a payment was paid, and each alerts Maria and leaves the registration's paid sum, its confirmation and the e-course access as they are until she acts:
   - the bank voids it (VOIDED): the payment is stored as failed with its paid time kept, and Maksed shows it as "Tühistatud pangas" (under "Ebaõnnestunud", with "Kontrolli Montonios");
   - a refund (REFUNDED, PARTIALLY_REFUNDED): stored as "Tagastatud", a partial one too (Maria's mail says which); alert "Kontrolli Montonios";
   - a second order of the same payment is paid as well: "Topeltmakse", once for each second order, with that order's own amount in the mail; its money is counted nowhere, and Maria refunds one of the two.
5. **Refunds** are made in Montonio's own Partner System (Orders → the order → Refund). The Refund button exists for card payments, and for bank payments only when Montonio's "Refundable bank payments" service is on for the store (Montonio's help centre, "How to make refunds from the Partner System"); for a regular bank payment there is no button, and Maria returns the money by a bank transfer of her own. The app learns of a refund from Montonio's refund notice: a webhook of its own to the order's `notificationUrl`, `{ "refundToken": "…" }`, sent whenever a refund's status changes (Montonio's developer documentation, Stargate → Refunds and Webhooks). The token is verified as an order token is (HS256 with the store's secret key; one that cannot be verified is a 400), the payment is found by its Montonio order (`orderUuid`), and Montonio is asked (`GET /orders/:uuid`): when the order reads REFUNDED or PARTIALLY_REFUNDED, the payment is marked "Tagastatud" and Maria is alerted, once (an order notice that says REFUNDED does the same). Nothing in the refund token itself, its status or its amount, is trusted: a refund that is still pending, or was rejected, leaves the order PAID and the payment as it is. A notice about an order no payment has (such as the second order Maria refunds after a "Topeltmakse") is answered 200 and changes nothing; when Montonio does not answer, the webhook answers 503 and Montonio sends the notice again. The daily check asks about pending payments only. A refund made outside Montonio's order, such as that bank transfer, is never seen: Maksed keeps saying "Makstud". Either way Maria adjusts or cancels the registration (or ends the e-course access) in the admin herself.
6. **The sandbox.** Its address is `sandbox-stargate.montonio.com/api` (production: `stargate.montonio.com/api`), chosen by `MONTONIO_ENV`. Montonio's public documentation names no test banks for the bank links: what the sandbox's bank page offers is found by trying it (write it here after the first go-live). For the card, Montonio's help centre gives a test card for sandbox mode with the sandbox keys ([How to test card payments in your store?](https://help.montonio.com/en/articles/157815-how-to-test-card-payments-in-your-store)): `5577 0000 5577 0004`, 03/30, CVC 737, an amount of at least €0.50; its further test cards and cases are Adyen's. The developer documentation's older pages (Payments V1) say that card payments are not available in the sandbox, so if the card method is missing there, ask Montonio's support before suspecting the app. A paid or failed bank flow cannot be produced automatically: it is a check by hand (the go-live, `docs/launch-checklist.md` section 10). **Each environment has its own reference prefix**, because a local database numbers its payments from 1 as production's does: production's references are `MSLAB-M<id>` (on the production deployment, `VERCEL_ENV=production`; its existing rows and orders keep them), a preview's `MSLAB-P<id>`, and those of this machine (`next dev`, the e2e run, a local production build) `MSLAB-L<id>` (`MONTONIO_REFERENCE_PREFIX` overrides it; section 2). So while production runs on the sandbox store, a local run with the same sandbox keys never overwrites a production order of the same reference. Its webhook still goes to its own `SITE_URL`, which may be the public site's (the default of `.env.example`): production answers a token whose reference does not carry its own prefix with a 200, logs `[payments] an order token for a reference of another environment: nothing to settle` (no reference) and changes nothing, and the local payment is never settled by its webhook (for trying the flow by hand, set `SITE_URL` to the local address, or let the return settle it). Test locally with the e2e run's fake Montonio, or with a sandbox store of its own, where you can.
7. **The logs.** `[payments] payment N: started` (or `sent again`), `… paid`, `… failed`, and, when Maria is alerted, `… held, Maria is alerted` (also `voided`, `refunded`, `double`; these are written at error level), `[payments] webhook: a token that cannot be verified (signature)` (the code can also be `malformed`, `alg` or `payload`; the return writes the same under `return:`; a refund notice's is `webhook: a refund token that cannot be verified (…)`), `[payments] a refund notice for an unknown order: nothing to settle`, `[payments] an order token for a reference of another environment: nothing to settle` (item 6), `[payments] a payment could not be settled (payment N): <error class>` (the daily check, section 5); never a key, a token, a `pay_token` or an address. Montonio's own error text is kept (`[payments] payment N: no order (rejected: HTTP 401 · STORE_NOT_FOUND …)`; `unreachable` and `bad_response` are the other two reasons). A line `[payments] <reason>: online payments are off` (once per instance) names the setting when `PAYMENT_PROVIDER` or the fake's address is wrong, or when only one of the two keys is set (`only one of MONTONIO_ACCESS_KEY and MONTONIO_SECRET_KEY is set`; the names only, never a value); no keys at all is silent. When Maria is alerted by the daily check or by an overpayment: `[payments] payment N: Montonio says paid but it could not be recorded, Maria is alerted`, `[payments] payment N: recorded after Maria was told it could not be, she is told now`, `[payments] payment N: over the price, Maria is alerted`.
8. **Rollback.** A rollback of the code past phase 2b (section 8) leaves the `payments` table with its two enum types and the registrations' two columns (`seat_hold_until`, `pay_token`) in place: migration 0006 is additive, and older code ignores them (a registration it stores gets its `pay_token` from the column's default). The older code has no payment routes, so it offers no payments and the three `MONTONIO_` variables do nothing there; but a payer who is at the bank when it goes back finds `/api/payments/return` answering 404, and the webhook's 404 is retried by Montonio over 48 hours. Payments started before the rollback and paid after it are settled once the code is back, by those retries or by the daily check (pending payments of up to 14 days): look at Maksed → Pooleli then.
