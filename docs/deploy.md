# MS LAB — how the site is hosted and deployed

Since 08.10.2026 the site is **https://mslab.ee**, on **Vercel**, on Maria's accounts (from 03.10 to 08.10.2026 it was https://mslab.diipsolutions.eu on Dim's, which now only redirects to mslab.ee). The Cloudflare Workers that served it before (`mslab-web`, the app, and `mslab-guide`, the old design hub) are retired and deleted; nothing in the repository deploys them any more. This file is the current setup. It holds variable **names** only: values are never written in the repository (it is public), and the secrets are entered by Dim himself in the Vercel dashboard.

## 2. Environment variables

Set in the Vercel project: Settings → Environment Variables (or `vercel env add <NAME> production`). A change reaches a deployment only when a **new** deployment is made. The build needs none of them: no page is prerendered from the database (`[locale]/layout.tsx` returns no static params on purpose; pages are rendered on the first request and then cached), and the start-up check runs when the server starts, not during the build, so `next build` succeeds with an empty environment. They are read at run time. Without a required variable every request answers 500 with an error that names the variable, never its value (`src/instrumentation.ts`, `src/server/env.ts`).

Every variable on Maria's Vercel project is a **plain** variable, the secrets too: that is the owner's choice (08.10.2026), so nothing is marked "Sensitive" there. "Secret" below means that the value never goes into the repository, a log or a message. To add a variable again (a new value), keep it plain too: `vercel env add <NAME> production --no-sensitive --force` (the CLI asks for the value; it is never typed into a file).

## 3. Deploying

**Normal way (once the branch is merged into `main`).** The project's Git integration (`mslabinformation-collab/mslab`) deploys `main` to production on every push, and any other branch or pull request to a preview URL (`*.vercel.app`, noindex like everything else). Nothing else is needed: the build is `next build` in `app/`. Database migrations are not part of it (section 6): apply a new one **before** the code that needs it goes live (one that drops something goes after the code that no longer reads it: section 6, and section 19, item 9 for 0016). Right before every push to `main`, stamp the test plan: `node tools/testplan-stamp.mjs` from `app/`, and commit the changed `app/src/data/testplan.json` with the merge (section 15; the tool prints how many `"deploy"` marks it replaced and leaves the file untouched when there are none).

**Previews.** A preview deployment builds, but no Preview environment variables are set (section 2), so the start-up check fails and every page and API request answers **500** (static files under `app/public`, such as `/guide/`, may still load). That is harmless: it touches no database and is behind Deployment Protection. Do not "fix" it by enabling the production variables for Preview. If a working preview is ever wanted, give Preview its own database and variables.

**After the first Git deploy of `main`.** That build puts live the R2 request handling and logging written after the CLI deploy of 03.10.2026, so check these once (replace the host if it has changed):

1. A key that does not exist answers 404 within a second: `curl -s -o /dev/null -w '%{http_code} %{time_total}s\n' https://mslab.ee/media/img/00000000-0000-4000-8000-000000000000.jpg`. A request that hangs means the R2 call is stuck (see the canary in `app/tests/unit/r2.test.ts`).
2. An image that exists (take an `/media/img/…` address from a course page) answers 200 with `cache-control: public, max-age=31536000, immutable`. Ask twice with `curl -sI`: `x-vercel-cache` is `MISS`, then `HIT`. The app also sends `Vercel-CDN-Cache-Control` so that the CDN keeps the image, but Vercel strips that header from the answer, so the `HIT` is the evidence.
3. One admin upload: sign in at `/admin`, upload a small image in a picture field (the upload route answers 201) and open its `/media/img/…` address. Uploads are never deleted today, so use a small image.
4. One manual cron run: Settings → Cron Jobs → Run on `/api/cron/sweep` answers 200, and the runtime log shows `[cron] sweep: N expired kv entries, N login codes, N sessions, N mail counters, N stuck video uploads deleted, N stuck processing videos found ready, N marked failed, N video rows left for the next run`.
5. Then the read-only checks at the end of this section.

**Manual fallback (the Vercel CLI).** The CLI reads the `.vercelignore` of the folder it runs in, so it works from the **repository root**, where the root `.vercelignore` is applied (an `app/.vercelignore` is not read there, and a deploy from `app/` is refused: the project's Root Directory `app` would become `app/app`). The root file is an allow-list of what `next build` in `app/` reads: `app/src`, `app/public`, `app/assets` (the certificate's fonts, phase 3d), `app/drizzle` and six files (`package.json`, `package-lock.json`, `next.config.ts`, `tsconfig.json`, `vercel.json`, `drizzle.config.ts`), about 450 files and 42 MB in October 2026. Everything else stays out, whatever lies around locally: `.wrangler`, `.open-next`, `.next`, `node_modules`, `.env*`, `.dev.vars*`, `.media-local`, test output and everything outside `app/` (`app/tests/unit/vercelignore.test.ts` guards this). It uploads the working tree, though, so uncommitted edits go up too. For a production deploy that is exactly the commit, deploy a clean copy of what is committed:

```
mkdir <scratch>
git archive HEAD app | tar -x -C <scratch>
mkdir <scratch>/.vercel && cp .vercel/project.json <scratch>/.vercel/
cd <scratch> && vercel deploy --prod
```

`.vercel/project.json` links the folder to the project (it is git-ignored; `vercel link` makes it). The CLI must be signed in to Maria's team `ms-lab`: Dim keeps that login in a global config folder of its own (`vercel --global-config ~/.vercel-mslabinformation …`). The CLI prints the deployment URL; the production alias moves to it when it is ready. `vercel rollback` or the dashboard (Deployments → a good one → Promote to Production) goes back to an earlier deployment.

After a deployment, check it read-only: `node tools/cache-smoke.mjs [base] [--only=A,B,C]` (A and B: 90 GET/HEAD requests over the main pages, the hub and a prototype, exit 1 on any answer that is not 2xx or 3xx, the `x-vercel-cache` counts printed; C: the client account's shells come from the cache without `set-cookie`, `/api/konto/me` answers 401 `private, no-store` and is never cached, a query on a shell gets a 303 into the fragment). **While the coming-soon gate is on (`SITE_GATE`, section 2; mslab.ee until the launch) every page is the one coming-soon page and `/api/konto/me` answers the gate's 404 `{ ok: false, error: "not_found" }` (`no-store`), so the tool notices that (`/api/konto/me` asked once first), says so, and does not check C: A and B then measure the coming-soon page's cache only, and the last line reads `PASS: 0 errors (part C not checked: …)`.** C runs for real against a local production build (`E2E_PROD_BUILD=1` builds and starts one on port 3100 for the e2e run; `next build && next start` with the local settings, no `SITE_GATE`, does it by hand) and against the site once `SITE_GATE` is gone. Run `node tools/cache-smoke.mjs` again right after the public launch. `E2E_BASE_URL=<site> E2E_ALLOW_REMOTE=1 npx playwright test headers --project=chromium` (from `app/`) for the headers. A run against a deployment is read-only: the form tests skip themselves and every POST is blocked.

## 4. DNS

The domain `mslab.ee` is registered, and its DNS hosted, at veebimajutus.ee (Elkdata). The apex `A` record points at Vercel (`76.76.21.21`) and `www` as Vercel's Domains page shows it; Resend's records (DKIM, SPF, return path) sit under `send.`; the mail records (MX and the rest) stay as they were. Vercel issues and renews the certificate itself. Keep any proxy out of the way: a proxy in front would hand every visitor the same address in `x-forwarded-for`, and the form rate limits would share one bucket.

The old name `mslab.diipsolutions.eu` (a `CNAME` in Dim's Cloudflare zone `diipsolutions.eu`) still points at Dim's old Vercel project, which only redirects to mslab.ee. Remove both after a few weeks (`docs/launch-checklist.md` section 1).

## 5. The daily cron

`app/vercel.json` has two crons, both once a day (the Hobby plan allows daily crons only; the exact minute within the hour varies): `GET /api/cron/sweep` at 03:00 UTC, described here, and the newsletter's daily job `GET /api/cron/uudiskiri` at 04:00 UTC (section 19, item 3). The sweep deletes the expired `kv_entries` rows (the rate-limit counters, which hold visitors' addresses, are gone a day after their window at the latest even when nobody submits a form), the expired client login codes (they hold the address), client sessions ended or expired more than 30 days ago, and daily mail counters older than 7 days. With online payments set up (section 11) it also asks Montonio (`GET /orders/:uuid`) about every pending payment that has an order and is older than 45 minutes (75 for a järelmaks, section 21) and younger than 14 days (oldest first, at most 50 a run, and no new question after the same 35 seconds of the run; one begun has Montonio's 15 s) and settles what Montonio says, through the one door every paid path ends in (`settlePayment`). Pending payments of 14 days, and those whose order was never created (no Montonio order 45 minutes after the start, 75 for a järelmaks), become failed (at most 50 a run, oldest first; a prepayment's seat hold ends with it). When unpaid seat holds ended in the last day, or a payment the check failed freed one, the calendar and the course pages are revalidated. A payment that cannot be settled (a settlement, or a stale row, that throws) is counted as an error and logged by its id and the error's class and code only: the run goes on with the next payment. Each of the two loops (the stale rows, the asking) stops early only on connection errors: after 3 of them in a row (`MAX_CONSECUTIVE_ERRORS` in `app/src/db/queries/payments.ts`; SQLSTATE class 08, the database shutting down, starting up or full — 57P01, 57P02, 57P03, 53300, as in a Railway restart — or the driver's own connection errors) the rest waits for the next day; any other error is that payment's own, and the loop goes on within its 50 rows (and, for the asking, its 35 seconds). When Montonio says a payment is PAID but the app cannot settle it (not a transient or connection error, which the next run gets past), Maria is alerted once: "Makse vajab kontrolli: {nimi}" (by mail and Telegram, remembered for 30 days in the KV as `pay:stuck:<id>`); the mail tells her to add it at the registration with „Lisa laekumine“, with the receipt (an e-course, which has no registration, she opens under Õpilased). A payment the webhook or the return records before that alert goes out gets no alert, and so no follow-up. Should the app record that payment after all (the webhook's retry, the return, or a later run, once the fault is gone), Maria gets one follow-up, "Makse on nüüd kirja pandud: {nimi}", which says: if she already added it with „Lisa laekumine“, take that receipt's payment back („Võta tasumine tagasi“) so it is not counted twice (section 22, item 4; a payment added without the receipt has no undo) (an e-course opened by hand needs nothing), and `pay:stuck:<id>` is removed. A payment Montonio does not answer for is only counted ("not answered") and asked about again the next day. The check asks about pending payments only: a refund made later reaches the app through Montonio's notice (section 11, item 5), never through the daily check. With Bunny set up (section 10) it also gives up lesson videos left unfinished for a day, at most 20 of each kind a run, and no new video is started after 35 seconds of the run (a video begun is finished, which takes about 20 seconds at most, so the run stays under `maxDuration`; the rest wait for the next day, and the log says how many). It also purges the lesson files an admin removed (the admin UX pass, piece 3a, section 23, item 4: „Eemalda“ only marks the row with `lesson_files.removed_at`, so the UndoBar can bring the file back): the rows marked 10 seconds ago or more are deleted, the row first and then its R2 object, in batches of 20 one after the other until a batch comes back short, at most 25 batches (500 files) and no new batch after the same 35 seconds (`drainRemovedLessonFiles`, `src/server/lesson-file-purge.ts`); what a bound leaves goes with the next run. A batch begun is finished: its 20 R2 deletes run one after the other and R2 has 10 s for each, so a hung R2 could keep one batch past the route's `maxDuration`; the rows are already gone then, and an object left behind only costs storage. „Eemalda“, the UndoBar's „Võta tagasi“ and each read of the course editor page purge the same way (one batch of 20, after the answer), so the sweep is the backstop for the last removal of a session. The purge never fails the sweep: a database failure is logged by its class and code only and counts as nothing purged; an R2 failure is logged the same way (no key), but its row is already deleted and counted as purged, and the object is left behind in R2 (an orphan that only costs storage). Hobby's functions may run up to 300 s: the route's `maxDuration = 60` is our own guard. An upload still `uploading` 24 hours after it began is asked about at Bunny and, if it never arrived, given up (the lesson gets its replaced video back, or has none, and only after that write is the video deleted from Bunny); a video still `processing` 24 hours after its upload began is asked about, kept if Bunny says ready, and otherwise marked failed, so the admin shows "Töötlemine ebaõnnestus" with "Lae uuesti üles". A ready video is never touched, and a replaced video that still plays is deleted only once the new one is ready. Vercel sends `Authorization: Bearer <CRON_SECRET>`; with no `CRON_SECRET` set, or any other header, the route answers 401. Crons run on the production deployment only. Check it under Settings → Cron Jobs (a run can be started there) and in the runtime logs: `[cron] sweep: N expired kv entries, N login codes, N sessions, N mail counters, N stuck video uploads deleted, N stuck processing videos found ready, N marked failed, N video rows left for the next run` (counts only: no video ids, no addresses), and, when the 35 seconds ran out, `[cron] sweep: no new video row started after 35 s`. The removed lesson files add `[cron] sweep: N removed lesson files purged` (only when N is above 0) and, when a bound ended the drain (25 batches or the 35 seconds; also when exactly 500 were due), `[cron] sweep: more removed lesson files are due than one run takes; the rest goes with the next run`. With online payments set up the log adds a second line, `[cron] sweep: payments N checked at Montonio, N settled, N not answered, N failed as stale, N left for the next run, N seat holds ended, N errors` (counts only: "settled" are the payments whose status changed, "failed as stale" the 14-day-old and never-created ones), and `[cron] sweep: no new payment asked about after 35 s` when the time ran out; without online payments there is no payments line at all. N errors above 0 counts the payments the app could not settle, or could not fail as stale: they stay pending, the line `[payments] a payment could not be settled (payment N): <error class>` names each by id, and the next day's run tries them again (look at them in Maksed → Pooleli). The 200 answer is JSON of counts: `ok`, `deleted`, `logins`, `sessions`, `mailDays`, `uploads`, `processingReady`, `processingFailed`, `videosLeft`, `files` (the removed lesson files purged this run: rows deleted, 0 when none was due) and, for the payments, `paymentsChecked`, `paymentsSettled`, `paymentsExpired` (failed as stale), `paymentsLeft` and `paymentsErrors` (all 0 without online payments); a database failure is a 500 `{ ok: false }`. A Bunny failure on the status read of one video is logged as `[video] stuck … not swept: <error class>` and only then is the video tried again the next day. When the Bunny delete fails after the lesson's row was already reset, the row is not tried again: the log says `[lesson] video not deleted: <error class>` (no id) and the empty video stays in Bunny. Compare Bunny's library list with the lessons now and then, and delete what no lesson uses.

## 6. Migrations on Railway

The SQL files are in `app/drizzle/`. They are additive, with two exceptions: 0010 dropped `courses.modules` (phase 3a's clean-up) and 0016 dropped the empty Resend parts the 18.10 newsletter build had added (the table `mail_suppressions` and three columns; section 19, item 9), both run after the code that no longer reads them. No other migration drops or rewrites data. Vercel does not run them. To apply the pending ones to the Railway database, from `app/`:

```
DATABASE_URL='postgres://…@<host>.proxy.rlwy.net:<port>/railway?sslmode=require' npm run db:migrate
```

- Take the **public** TCP proxy URL from the Postgres service of Maria's Railway project `mslab` (Connect → Public Network) and add `?sslmode=require`. Put it in the shell only: never in a file, never in the repository (`.env*` files are git-ignored, but an `.env` that a local `next dev` reads would then point the dev server at production data too).
- The SQL statements and read-only checks this guide gives for the Railway database (the ones in section 19, for example) Dim runs with `psql`, the same public URL taken into the shell (`psql "$DATABASE_URL"`) and never written down.
- `drizzle-kit migrate` applies what is not yet recorded in its own table, in order. ## 9. Hobby-plan limits to keep in mind

- 1 million function invocations a month and 100 GB of data transfer; an image is cached by Vercel's CDN (`Vercel-CDN-Cache-Control` on `/media`), the public pages by ISR.
- 4.5 MB request body: the upload limit in the app is 4 MB (the admin's browser shrinks images first).
- Cron jobs: once a day at most.
- A function that hangs would run for the plan's default 300 s: `/media` and the upload route set `maxDuration = 30`, and R2 gets 10 s to answer. The same holds for Bunny's API (10 s an answer; the account API and the webhook set 30). The daily cron sets 60 as its own guard (Hobby allows up to 300 s): at most 20 video rows of each kind, and no new one after 35 s of the run (a row begun takes about 20 s at most to finish: 35 + 20 is under 60); its payments check keeps to the same 35 s (a question to Montonio begun takes 15 s at most, and at most 50 are asked a run), and so does the drain of the removed lesson files (section 5). The newsletter's daily job (`/api/cron/uudiskiri`, section 19) sets 300 and keeps to 270 s of it: a mail begun at the end has Resend's 8 s, and once more after a 429, so 270 + 17 s and the queries stay under 300; its mails go 0.6 s apart (Resend answers 429 above about two requests a second), so the day's 70 take about a minute. `/admin/uudiskiri` sets `maxDuration = 120`: its server action „Saada kõigile“ sends the first batch within 60 s by the same rules, and the page's other actions are a few queries or one mail. 300 s on Hobby needs Fluid Compute: verify it on Vercel at the go-live, as for the protocol screen below. Montonio has 15 s to answer (`REQUEST_TIMEOUT_MS`); the webhook, the return, `/maksa/<token>`, `/api/konto` and the two pages whose forms start a payment (the course page, for the registration's prepayment, and the e-course cart) set `maxDuration = 30`. Online payments add no polling: a payment costs a few calls (its start, Montonio's webhook, the return), and Montonio retries a webhook over 48 hours until it gets a 200 or 201, so only a failing app costs more.
- A student watching a lesson posts her progress about every 15 s (about 240 function calls an hour of video); 500 hours watched a month is about 120 000 calls.
- The protocol screen (phase protocols, section 12) saves 1.5 s after Maria stops typing, when she leaves a box, when she switches student, when the tab is hidden and when she leaves the screen, and only when something is unsaved (merely opening a protocol or switching student posts nothing), and nothing runs on a timer while nothing changes. A failed save is tried again after 2, 5, 10, 20 and then every 30 s, and at once when the tablet is back online or the tab is shown again; a save the browser gets no answer to within 10 s is tried again. The screen also reads the server's text once each time it is opened (`GET /api/admin/protokoll`), and again after a failed read (on the same steps), when the page comes back from the browser's cache and when a tab hidden for over 5 minutes is shown. A course day of six students is a few hundred calls. `/api/admin/protokoll` (both methods) sets `maxDuration = 30`; a save body is at most 631 296 characters (`MAX_SAVE_CHARS`, more is a 413), under 2 MB and far inside the 4.5 MB limit. `/admin/protokollid` sets `maxDuration = 300`: the sends are its server actions, and the mails of „Saada kõigile ({n})“ ("Lukusta ja saada kõik" before the admin UX pass, piece 2) go out after the answer as one task, about 0.8 s apart (100 students at most, about 80 s). 300 s on Hobby needs Fluid Compute: verify it on Vercel at the go-live. The protocol mails count in Resend's 100 a day, though not in the app's daily caps.

Paid is a floor: a later ABANDONED or FAILED changes nothing. Three things happen after a payment was paid, and each alerts Maria and leaves the registration's paid sum, its confirmation and the e-course access as they are until she acts:
   - the bank voids it (VOIDED): the payment is stored as failed with its paid time kept, and Maksed shows it as "Tühistatud pangas" (under "Ebaõnnestunud", with "Kontrolli Montonios");
   - a refund (REFUNDED, PARTIALLY_REFUNDED): stored as "Tagastatud", a partial one too (Maria's mail says which); alert "Kontrolli Montonios";
   - a second order of the same payment is paid as well: "Topeltmakse", once for each second order, with that order's own amount in the mail; its money is counted nowhere, and Maria refunds one of the two. A payment that is itself the second of something paid in full already, such as a late järelmaks after a bank payment, is held the same way (section 21, item 5).
5. **Refunds** are made in Montonio's own Partner System (Orders → the order → Refund). The Refund button exists for card payments, and for bank payments only when Montonio's "Refundable bank payments" service is on for the store (Montonio's help centre, "How to make refunds from the Partner System"); for a regular bank payment there is no button, and Maria returns the money by a bank transfer of her own. The app learns of a refund from Montonio's refund notice: a webhook of its own to the order's `notificationUrl`, `{ "refundToken": "…" }`, sent whenever a refund's status changes (Montonio's developer documentation, Stargate → Refunds and Webhooks). The token is verified as an order token is (HS256 with the store's secret key; one that cannot be verified is a 400), the payment is found by its Montonio order (`orderUuid`), and Montonio is asked (`GET /orders/:uuid`): when the order reads REFUNDED or PARTIALLY_REFUNDED, the payment is marked "Tagastatud" and Maria is alerted, once (an order notice that says REFUNDED does the same). Nothing in the refund token itself, its status or its amount, is trusted: a refund that is still pending, or was rejected, leaves the order PAID and the payment as it is. A notice about an order no payment has (such as the second order Maria refunds after a "Topeltmakse") is answered 200 and changes nothing; when Montonio does not answer, the webhook answers 503 and Montonio sends the notice again. The daily check asks about pending payments only. A refund made outside Montonio's order, such as that bank transfer, is never seen: Maksed keeps saying "Makstud". Either way Maria adjusts or cancels the registration (or ends the e-course access) in the admin herself.
6. **The sandbox.** Its address is `sandbox-stargate.montonio.com/api` (production: `stargate.montonio.com/api`), chosen by `MONTONIO_ENV`. Montonio's public documentation names no test banks for the bank links: what the sandbox's bank page offers is found by trying it (write it here after the first go-live). For the card, Montonio's help centre gives a test card for sandbox mode with the sandbox keys ([How to test card payments in your store?](https://help.montonio.com/en/articles/157815-how-to-test-card-payments-in-your-store)): `5577 0000 5577 0004`, 03/30, CVC 737, an amount of at least €0.50; its further test cards and cases are Adyen's. The developer documentation's older pages (Payments V1) say that card payments are not available in the sandbox, so if the card method is missing there, ask Montonio's support before suspecting the app. A paid or failed bank flow cannot be produced automatically: it is a check by hand (the go-live, `docs/launch-checklist.md` section 10). **Each environment has its own reference prefix**, because a local database numbers its payments from 1 as production's does: production's references are `MSLAB-M<id>` (on the production deployment, `VERCEL_ENV=production`; its existing rows and orders keep them), a preview's `MSLAB-P<id>`, and those of this machine (`next dev`, the e2e run, a local production build) `MSLAB-L<id>` (`MONTONIO_REFERENCE_PREFIX` overrides it; section 2). So while production runs on the sandbox store, a local run with the same sandbox keys never overwrites a production order of the same reference. Its webhook still goes to its own `SITE_URL`, which may be the public site's (the default of `.env.example`): production answers a token whose reference does not carry its own prefix with a 200, logs `[payments] an order token for a reference of another environment: nothing to settle` (no reference) and changes nothing, and the local payment is never settled by its webhook (for trying the flow by hand, set `SITE_URL` to the local address, or let the return settle it). Test locally with the e2e run's fake Montonio, or with a sandbox store of its own, where you can.
7. **The logs.** `[payments] payment N: started` (or `sent again`), `… paid`, `… failed`, and, when Maria is alerted, `… held, Maria is alerted` (also `voided`, `refunded`, `double`; these are written at error level), `[payments] webhook: a token that cannot be verified (signature)` (the code can also be `malformed`, `alg` or `payload`; the return writes the same under `return:`; a refund notice's is `webhook: a refund token that cannot be verified (…)`), `[payments] a refund notice for an unknown order: nothing to settle`, `[payments] an order token for a reference of another environment: nothing to settle` (item 6), `[payments] a payment could not be settled (payment N): <error class>` (the daily check, section 5); never a key, a token, a `pay_token` or an address. Montonio's own error text is kept (`[payments] payment N: no order (rejected: HTTP 401 · STORE_NOT_FOUND …)`; `unreachable` and `bad_response` are the other two reasons). A line `[payments] <reason>: online payments are off` (once per instance) names the setting when `PAYMENT_PROVIDER` or the fake's address is wrong, or when only one of the two keys is set (`only one of MONTONIO_ACCESS_KEY and MONTONIO_SECRET_KEY is set`; the names only, never a value); no keys at all is silent. When Maria is alerted by the daily check or by an overpayment: `[payments] payment N: Montonio says paid but it could not be recorded, Maria is alerted`, `[payments] payment N: recorded after Maria was told it could not be, she is told now`, `[payments] payment N: over the price, Maria is alerted`.
8. **Rollback.** A rollback of the code past phase 2b (section 8) leaves the `payments` table with its two enum types and the registrations' two columns (`seat_hold_until`, `pay_token`) in place: migration 0006 is additive, and older code ignores them (a registration it stores gets its `pay_token` from the column's default). The older code has no payment routes, so it offers no payments and the three `MONTONIO_` variables do nothing there; but a payer who is at the bank when it goes back finds `/api/payments/return` answering 404, and the webhook's 404 is retried by Montonio over 48 hours. Payments started before the rollback and paid after it are settled once the code is back, by those retries or by the daily check (pending payments of up to 14 days): look at Maksed → Pooleli then.

## 12. Protocols and the feedback form

Maria writes one protocol per student on the course day and sends it at the end; the student reads it in her account and may answer Maria's feedback form there (phase protocols, spec `docs/superpowers/specs/2026-10-12-protocols-design.md`).

1. **What runs where.** The screen is `/admin/protokollid?sessioon=<id>` (from Kalender's session drawer, "Protokollid", and from the overview's "Täna" card, which lists today's scheduled sessions of contact courses, Tallinn date, and is hidden on a day with none) or `?registreering=<id>` (from a registration's drawer, "Ava protokoll"). Its autosave posts to `POST /api/admin/protokoll`, and the screen reads the server's text again through `GET /api/admin/protokoll?sessioon=<id>` or `?registreering=<id>` (item 3); both are behind `withAdmin`, and `/api/admin` passes the coming-soon gate like the upload route does. The sends are server actions called from the page (`adminAction`, `src/server/actions/admin-protocols.ts`). The student's pages are the static shells `/konto/protokoll#id=<registration>` and `/konto/tagasiside#id=<registration>` (`/ru/…` in Russian; the id is in the fragment because an account page never has a query); their data is `GET /api/konto/protokoll?id=`, `GET|POST /api/konto/tagasiside` and `POST /api/konto/tagasiside/peida` (`private, no-store`; behind the coming-soon gate until the launch, like every account route). Maria reads the answers on `/admin/tagasiside` and in the Õpilased and Registreerimised drawers. No new variable, no cron, and nothing revalidates a page: the student's pages are static shells that read the API.
2. **The data.** Migration `0007_protocols` (additive; it runs on Railway before the deploy, section 6, and the code that is live now does not name it): `courses.protocol_stages` (the course's headings, edited in the course editor's "Protokolli punktid"), `protocols` and `course_feedback` (one row each per registration, deleted with it). A protocol is created by its first save, with the course's headings as they are then; a later change of the headings reaches only protocols not created yet. The status (Mustand, Saadetud, Muudetud) is computed from `version`, `sent_at` and `sent_version`, never stored. The student is only ever served `sent`, the copy frozen at the send. The drop of `courses.modules` is migration 0010 (0008 is the e-course completion's and 0009 the certificate's; code first, then the migration, as planned in phase 3a).
3. **The autosave, the tablet and the reads.** Every save carries the version the screen has, the protocol's row it builds on (`protocolId`) and the headings it shows. A save from an older version whose text differs from what is stored is refused (409) with what is stored, and so is a save built on another row: a protocol deleted with the account and made again starts again at version 1, so the version alone could not tell a screen (or a browser copy) of the old protocol from the new one. A copy of the old row found in the browser is never resumed onto the new one: its words go into the notice. A save without `protocolId` (a screen loaded before this rule) is checked by the version only. **Upgrade caveat:** a browser copy written before this deploy has no row in it, so it is resumed by the version alone; if such a protocol was deleted with the account and made again up to that same version meanwhile, the old copy would be resumed and saved onto the new row. Before deploying, make sure no tablet shows a "Salvestamata" chip (every text confirmed), so no such copy is left; after the deploy every copy carries its row. A read of an older row than the one the screen knows (a read made before the delete, answering late) is ignored. The screen (`src/components/admin/protocol-autosave.ts`) decides what a refusal means. If the stored text is one that this screen itself sent earlier without hearing the answer (the answer was lost on the way), it is its own save: the screen takes the version and saves its newer text on top, with no notice. Only a stored text that this screen never sent opens the notice "Seda protokolli muudeti vahepeal teises seadmes või aknas." (`protocols.conflict` in `src/i18n/dict/admin.ts`, which holds the other `protocols.…` texts named here too): the stored text is shown, with this screen's unsaved words under it, and the notice stays (also across a reload) until Maria presses "Selge". A protocol with an open notice is not sent: a single "Saada" says "Vaata enne saatmist üle teises seadmes tehtud muudatus ja vajuta „Selge“." (`protocols.sendErrors.review`), and the bulk send leaves it out (item 4). A protocol is saved only when something is unsaved (merely opening a protocol or switching student posts nothing): nothing is posted for a protocol whose boxes were never typed in, since a first save would create it as a "Mustand". Until the server confirms a text, the browser keeps it in `localStorage`, under keys of its own page load, so that one tab never overwrites or removes another's: `mslab-protocol:<registration id>:<tab>` (the text), `mslab-protocol-sent:<registration id>:<tab>` (the texts sent without an answer) and `mslab-protocol-conflict:<registration id>:<tab>` (the notice's words, until "Selge"). A page that opens finds the keys of a closed tab (or of an older screen, which had no tab part), resumes the newest text and puts the words of the others into its notice; those keys go once their words are kept by this page or on the server. A save that fails is tried again after 2, 5, 10, 20 and then every 30 s, and at once when the tablet is back online or the tab is shown again; a save the browser gets no answer to within 10 s is tried again. A tab that is hidden sends its waiting save at once, and a page that is put away (`pagehide`) sends it as a `keepalive` request while the bodies fit the browsers' 64 KB together, else it leaves it to the copy in `localStorage`. Leaving the screen for another admin page sends the waiting save too, once: after the save on its way (never beside it) and from the version that save got; its text stays in `localStorage` until a later visit finds it stored. The student's chip says "Salvestamata" while her text is not confirmed. So on the tablet: never clear the browser's site data, and never use a private window, while a chip says "Salvestamata"; a browser that cannot keep the text (its storage full or blocked) says so under that protocol (`protocols.notKept`, "Seda teksti ei saa selles seadmes hoida …": do not close the page). With the storage full, the notice's key is written first and, failing that, its words stay in the text's own copy: the words are never dropped. While a send is on its way its protocol is read-only. A box over 10 000 characters is never cut: it says so, and nothing of that student is saved until it is shorter.

   The browser's Back button restores the page from Next.js's client router copy of the visit, which is older than what was saved since. So the screen never takes its text for the server's: each time it is opened it reads the server's text again (`GET /api/admin/protokoll`, one call), and until it has, it says "Kontrollin salvestatud teksti…" (`protocols.checking`) instead of "Salvestatud". It reads again after a failed read (2, 5, 10, 20, then every 30 s), when the network is back, when the page comes back from the browser's cache, and when a tab that was hidden for more than 5 minutes is shown. A newer text of the server is taken silently by a protocol with nothing unsaved, and goes the way of a refusal (the notice, the words kept) when this screen has text of its own. A protocol whose save is queued or on its way is left alone by the read until that save is over: when the save's answer was the server's word (saved or refused) the read is dropped, else it is taken then. A read answered 401 or 403 says "Salvestamata — logi uuesti sisse." (`protocols.signedOut`; the text stays in the browser); a 404, or a student the answer does not list (cancelled or moved meanwhile), is marked gone ("Seda registreeringut enam ei ole.", `protocols.gone`) and keeps her unsaved text. (The read is a GET of its own; `router.refresh()` is not used, because a refresh that fails offline makes Next.js leave the page for the browser's error page.)
4. **A send.** One transaction per student, the locks in one order: the address (`client-auth.ts lockAddress`), then the registration (`seats.ts lockRegistration`), then the protocol row (`FOR UPDATE`). That order is fixed: the logins and `addClient` take the address first and then write registrations, so another order could deadlock. The send freezes `sent`, `sent_at` and `sent_version`, makes her account when she has none (`addClient`, which also links that address's other unlinked registrations and requests, as "Lisa õpilane" does) and links the registration. A cancelled registration is never sent; an empty protocol is refused. Two taps or two devices sending the same version at once send it once, with one mail (`tests/e2e/protocols-race.spec.ts`, which also pins the lock order). The per-student send („Saada protokoll {eesnimi}le“, and „… uuesti“ after a change; "Saada" and "Saada uuesti" before the admin UX pass, piece 2) saves first, with the protocol read-only, and send the version the server confirmed, with the row it is of (`protocolId`: another row, a protocol deleted with the account and made again, is "stale"; a send without one, from a screen loaded before this rule, goes by the version); a screen that still says "Kontrollin salvestatud teksti…" waits up to 10 s for the server's text first, and when that text differs from what the screen showed it shows the new text and does not send (`protocols.sendErrors.refreshed`: "Protokolli muudeti vahepeal mujal ja siin on nüüd uus tekst. Vaata see üle ja saada siis."). „Saada kõigile ({n})“ ("Lukusta ja saada kõik" before piece 2) opens one ConfirmPanel („Kas saadan {n} protokolli?“, yes „Jah, saada {n} protokolli“, no „Katkesta“): who will get a protocol, who is skipped because hers is empty, who has hers already, whose own "Saada" is on its way ("Saatmine juba käib: {names}", `protocols.confirm.onItsWay`), and whose notice is open ("Vaata enne üle ja vajuta „Selge“: {names}", `protocols.confirm.review`); the last two are left out. On the yes each of the others is saved on its own, and the ones whose save the server confirmed go in one server action (at most 100) that sends each in its own transaction. One protocol that cannot be saved or sent never stops the others, and the summary names the students by reason, one line a reason. The sends are called from `/admin/protokollid`, and the mails of a bulk send go out after the answer (item 5), so the page sets `maxDuration = 300` (`tests/unit/protocol-page.test.ts` pins it). **On Hobby, 300 s needs Fluid Compute: verify on Vercel at the go-live** that the project runs with it and that the deployment built with `maxDuration = 300` for `/admin/protokollid`; a course day of four to six students needs about 5 s. The account's deletion (`client-data.ts deleteClient`) takes the address and then her registrations (`FOR UPDATE`) before it deletes their protocols and feedback, the same order, so it never deadlocks with a send (a different pair, an e-course's invoice catch-up against the same deletion, can in theory: section 16, item 3); the registrations and the payments stay. A later send to such a registration makes a new account (the owner approved this).
5. **The mails.** After the commit, as one task of `after()` for each call, one mail after another, `MAIL_GAP_MS` = 600 ms apart (Resend answers 429 above about two requests a second; with the request itself a mail takes about 0.8 s, so 100 mails take about 80 s). The shared `sendMail` also tries once more after about 1 s (`RATE_LIMIT_RETRY_MS` in `src/server/notify.ts`) when Resend says it is asked too fast, and not again; a used-up quota (a 429 whose name says quota) is not retried. The mails are "Sinu koolituse protokoll on valmis" (the first send, with the feedback form's link: the line "Soovi korral jäta meile tagasisidet") or "Sinu koolituse protokolli on uuendatud" (a send again, without it), in the registration's language. The button is `/api/konto/verify?t=<token>&p=<registration>` (a normal client login made with the mail, 30 minutes): it signs her in on the device that opens it, as every login link does (her other session ends), and lands on `/konto/protokoll#sisse&id=<registration>`. The six-digit code is shown under the button, as in the e-course mail. An address that has its 3 live logins already, or a login that cannot be made (logged, below), gets the mail without a login: its button then opens `/konto/protokoll#id=<registration>`, which asks her to sign in. No mail holds a note. These mails are not counted in the daily login-mail cap (they follow Maria's own sends, a handful a course day), though they count in Resend's 100 a day, and a sample address (`@example.test`) is never mailed (and nothing is logged for it). A failed mail never undoes the send: the student sees the protocol on her dashboard all the same ("Vaata protokolli"). A mail cannot be sent again for the same version (a second "Saada" of it is "already"): if one is lost, Maria changes the protocol (a saved change raises the version) and sends it with "Saada uuesti", which mails "uuendatud" without the feedback line.
6. **The feedback form.** It opens (`src/domain/protocols.ts feedbackOpen`) when the registration is not cancelled and its protocol has been sent (the first send opens it), or when it is a group registration whose session started before today (Tallinn time) and was not called off, so on the day after a group course day, protocol or no protocol. The rule does not look at the payment: a registration still awaiting its prepayment whose session has passed gets the card too. Never for a cancelled registration. The dashboard's card "Kuidas koolitus läks?" shows while the form is open and she has neither answered nor pressed "Ei soovi"; "Ei soovi" hides only the card, and the first mail's link still opens the form. One answer per registration (a second is a 409, and the form says "Tagasiside on juba saadetud. Aitäh!"). At most 10 answers and "Ei soovi"s a client an hour, counted together. Each answer sends Maria "Uus tagasiside: {nimi}, {koolitus}, {score}/10" (without the score part when none was given) by mail (to `MARIA_EMAIL`, reply to the student) and Telegram, after the response, also for a sample student; its questions and options are in her Estonian wording whatever language the student answered in.
7. **The logs.** `[protocols] registration N: sent` (or `sent again`), `[protocols] registration N: the mail sent` (or, at error level, `the mail was not sent`: Resend did not take it), `[protocols] registration N: the mail failed: <error class>`, `[protocols] registration N: login code unavailable, the mail goes without it: <error class>`, `[protocols] registration N: the send failed: <error class>`, `[protocols] registration N: the save failed: <error class>`, `[protocols] session N: the screen could not be read: <error class>` (or `registration N`), `[protocols] a mail failed: <error class>` (a mail job that threw outside its own catch); `[notify] Resend asks for fewer requests: the e-mail is tried once more`; `[feedback] registration N: submitted`, `[feedback] registration N: Maria notified by e-mail: true|false, Telegram: true|false`, `[account] feedback rate limited`. An error class is the class, the code and the HTTP status only. Never a note, an answer, a name or an address; a sample address's mail leaves no line.
8. **Rollback.** A rollback of the code past this phase (section 8) leaves the three additions of 0007 in place; the older code ignores them. It has no protocol screen and no `/konto/protokoll` or `/konto/tagasiside`: a protocol mail sent before then lands on a 404 until the code is back (the feedback link of a first mail too); only a button whose login is still valid signs her in, and the older code takes her to her dashboard, which has no protocol card. Its account deletion does not know the two tables, so an account deleted meanwhile keeps its protocols and feedback: delete them by hand afterwards, by the registrations that the deletion unlinked (Railway, from `app/` with the URL in the shell only, section 6; read the rows first: a sent protocol or a feedback answer whose registration has no `client_id` belongs to a deleted account, since a send makes the account and only the owner answers the form), or a new account for the same address would be shown the old protocol.

## 13. E-course completion: the knowledge test, the practical work, "Lõpetatud"

An e-course ends on the platform: the lessons, Maria's knowledge test, the practical work with photos that Maria assesses, then "Lõpetatud" (spec `docs/superpowers/specs/2026-10-13-ecourse-completion-design.md`, plan `docs/superpowers/plans/2026-10-13-ecourse-completion.md`).

1. **What runs where.**
   - **The student's pages:** the static shells `/konto/kursus/<slug>/test` and `/konto/kursus/<slug>/praktiline` (`/ru/…` in Russian), and the "Lõpetamine" block on `/konto/kursus/<slug>`. Their data is `GET|POST /api/konto/kursus/<slug>/test`, `POST …/test/uuesti`, `GET /api/konto/kursus/<slug>/praktiline`, `POST …/praktiline/foto` (multipart), `DELETE …/praktiline/foto/<id>` and `POST …/praktiline/saada`. A photo is `GET /api/konto/praktiline/foto/<id>` (`…/pisi` the thumbnail): a 302 to a 5-minute signed R2 address, `Referrer-Policy: no-referrer`. All are `private, no-store` and behind the coming-soon gate until the launch, like every account route.
   - **Maria's pages:**
     - "Hindamine" (`/admin/hindamine`, after "Registreerimised", its badge the number waiting; the overview's „Sinu järjekord“ row „Ootab hindamist“);
     - the test review (`/admin/hindamine/test?id=<attempt>`; `?ligipaas=<access>` lists a student's attempts);
     - the practical assessment, which is the protocol screen at `/admin/protokollid?ligipaas=<access>`. A photo opens full-screen (swipe, pinch zoom, one finger pans while zoomed); its "Ava täissuuruses" opens `GET /api/admin/foto/<id>` in a tab of its own, where the tablet's own image viewer zooms and pans;
     - the student's drawer in Õpilased: each e-course's steps, "Lisa protokoll" / "Ava protokoll", "Testi katsed" and "Ava test uuesti".
   - **Maria's endpoints:** its notes autosave through `POST /api/admin/protokoll` (the body names `accessId`; the screen reads the server's text again through `GET /api/admin/protokoll?ligipaas=<access>`), each verdict tap through `POST /api/admin/hinnang`, and the photos through `GET /api/admin/foto/<id>` (`?v=pisi`). "Saada hinnang", the review's "Saada" and "Ava test uuesti" are server actions (`src/server/actions/admin-assessment.ts`). `POST /api/admin/hinnang` and `GET /api/admin/foto/<id>` set `maxDuration = 30`; the protocol page keeps its 300 (section 9).
   - **Configuration:** no new variable, no cron.
2. **The data.** Migration `0008_ecourse_completion` is additive. It runs on Railway before the deploy (section 6), and the live code does not name what it adds; its one loosening, `protocols.registration_id` becoming nullable, is harmless to code that always writes it.
   - `course_tests`: one row per course, holding the questions with the answer key, the pass mark and the tries. It is kept apart from `courses`, whose rows the public pages read. A course without a row has no test.
   - `course_access.extra_tries` ("Ava test uuesti" adds the course's tries) and `course_access.completed_at` (set once, never cleared; phase 3d reads it).
   - `test_attempts`: one row per submitted try, each with the frozen copy of the questions it answered, its answers, its score, its status (failed, review, fix, passed) and Maria's review.
   - `protocols.access_id`: a protocol belongs to a registration or to an e-course access, exactly one (`protocols_one_owner`). Also `verdicts` (Maria's draft verdict for each point), `round` (how many times the student has sent her work), `submitted_at` and `sent_round` (the round Maria's last sent assessment was about). What she sent is frozen in `sent`, with its own verdicts.
   - `practical_photos`: one row per photo, with private R2 keys `practical/<uuid>.jpg` and `practical/<uuid>-t.jpg`; earlier rounds are kept.
   - The drop of `courses.modules` is migration 0010 (0009 is the certificate's; code first, then the migration, as planned in phase 3a).
3. **The rules.**
   - **Completion:** `completed_at` is set by one function (`completeIfDone`, `src/server/completion.ts`), once, and never cleared: not when the access later ends, and not when Maria adds a lesson or a question. It runs after four things:
     - the student's last lesson is done ("Märgi tehtuks", or a video watched to 90 %);
     - a test is passed (the student's submit, when the test has no open question, or Maria's review of the open answers);
     - Maria's "Saada hinnang" approves every point;
     - the student's e-course page loads (`GET /api/konto/kursus/<slug>`) while the access is active and not completed. This heals a completion missed by a failed check, and the accesses whose steps were all done before the deploy. Maria's read-only view of a student's course does not run it.
   - **Completion, the edges:** an empty e-course (no visible lesson, no question and no point) never completes; one with no visible lesson but a test or points completes when those are done. A revoked access never completes; an expired one can (Maria still assesses it). Only the call that sets the date mails "Palju õnne!", after the commit. A failed completion check after a lesson is logged (`[completion] access N: the check failed: <error class>`) and the lesson still answers normally; the next page load checks again. A failed check on the page load is logged the same way and the page loads as it was.
   - **The test:**
     - The test opens when every visible lesson is done, and stays open once an attempt exists (a lesson added later does not lock it again). The practical work opens when the test is passed, or, for a course without questions, once the lessons are done; once a round is submitted, a question added later does not lock it. A step once passed stays passed.
     - A try is a submitted attempt, and the same answers sent twice (a double tap, a second device) are one attempt. Rewriting the answers Maria marked "Paranda" uses none. A submit made from questions Maria changed meanwhile is refused ("Test on vahepeal muutunud, laadi leht uuesti") and writes nothing; an old attempt keeps its frozen copy of the questions. The tries are the course's, plus what each "Ava test uuesti" added.
     - The student never sees the answer key: only the score and the numbers of the wrong questions. The open answers wait for Maria's review (in "Hindamine"), which marks each "Kinnitatud" or "Paranda" (a comment is needed on a "Paranda").
   - **The practical work:**
     - The first round needs a photo on every point; later rounds only on the "Paranda" points. There are at most 3 photos per point and round. A photo of a round already sent is kept and can no longer be removed.
     - "Saada hindamiseks" raises the round and resets the "Paranda" verdicts for Maria's next look. What the student is shown stays Maria's last sent copy.
     - "Saada hinnang" needs every point marked and a note under every "Paranda". It freezes the notes and the verdicts into `sent`, which is all the student is ever shown. When every point is approved, the course is completed. After that the verdicts are locked, and a change of the notes is sent as "uuendatud".
     - An e-course without points has no photos and no assessment: Maria can only send her notes, and the student reads them on the same page.
     - Points added to a course after a student has completed it do not reach her: with no protocol yet her practical page is read-only ("Lõpetatud"), and a photo or a send is refused (`closed`), as "Hindamine" lists no completed access. A protocol made before the completion keeps the work as it was.
   - **Maria's screens go stale safely.**
     - "Saada hinnang" and every verdict tap carry the round Maria's screen shows, with the protocol's row ("Saada hinnang" also the notes' version). A screen of an older round is refused as stale: nothing is stored or sent, and the screen reads again and shows "Õpilane saatis vahepeal uue korra. Vaata see üle." A resubmission never raises the notes' version, so only the round tells such a screen from the stored work; Maria never approves photos she has not seen. A tap refused for another reason (nothing sent yet, every point approved and so the verdicts locked, a revoked access) says "Hinnangut ei salvestatud: töö seis muutus vahepeal. Vaata punktid üle." and the screen reads again.
     - The test review sends the `submittedAt` of the answers it showed; a mismatch (the student has rewritten them since) is stale, as is an attempt reviewed meanwhile on another device. Nothing is stored, and the reload shows the answers as they are.
     - "Ava test uuesti" asks with a ConfirmPanel („Kas avan testi „{course}“ uuesti?“, the line „Õpilane saab sama palju katseid juurde ja kirja.“, „Jah, ava“, „Katkesta“). Once the test is open the action revalidates the whole admin, so the menu badge and the overview's queue count one less at once: on Hindamine the row leaves the list, the page's status line says „Test uuesti avatud: {nimi}, katseid jäänud {n}.“ (it names the student, because her row is gone) and the focus goes to the next row (or the heading); in the student's drawer the line stays.
     - The assessment screen's round line ("Praktiline töö, N. kord") and status follow its reads (there is no confirmation panel any more: „Saada hinnang · {k} kinnitatud, {p} paranda“ sends at once, with its refusals, and „Kinnita kõik“ is a separate button). An "already" answer reads the server again, so the screen shows its status. A send with no answer says "Vastust ei tulnud: kontrollin, kas protokoll saadeti. …" and reads again; when the read shows the send done (the notes' version sent, the round assessed with the verdicts sent) the line goes and the screen locks.
   - **An access that ends:** an expired access reads its results read-only (no submit, no new photo), and Maria can still assess. Reopening the test on an expired access adds the tries but sends no mail, and the "Test on sooritatud", "Vaata üle oma testi vastused" and "Sinu praktiline töö on hinnatud" mails are not sent to an expired access either (the "Palju õnne!" mail and the notes-only protocol mails still go). A revoked access answers 404 on the student's pages, and its items leave "Hindamine".
   - **Lock order:** every write about one access that the student or Maria makes (a test submit, a rewrite, a review, "Ava test uuesti"; a photo, its removal, "Saada hindamiseks"; a verdict tap, "Saada hinnang") takes the `course_access` row (`FOR UPDATE`) first, then its protocol, then the attempts or the photos. Two devices or a double tap therefore make one try, one round and never a fourth photo (`tests/e2e/completion-race.spec.ts`). The notes' autosave takes no lock: it is one conditional statement that waits behind a held row and then checks its version.
   - **Deletion:** the account's deletion (`deleteClient`) takes the address, then her registrations, then her access rows (`FOR UPDATE`, the order a photo upload takes), lists the photo files inside its own transaction (it returns `photoKeys`) and deletes the client, which cascades to the access rows, attempts, protocols and photo rows. The files are removed from R2 after the answer, one by one. A photo upload in flight is either in the list or, after the commit, finds the access gone and removes its own files. A failed removal is logged by the client's id (not a protocol id), and the file stays in the bucket with no row naming it: delete it by hand (its key is under `practical/`).
4. **The photos.**
   - **In the browser:** the student's browser shrinks each photo before it is sent: JPEG, at most 2048 px (quality 0.85, then 0.7, then 1600 px at 0.7 while it is over 2 MB), typically about 0.5–1 MB, plus a 480 px thumbnail. The re-encode drops all metadata, including the GPS position, and turns the photo upright by its orientation tag. A file the browser cannot open (a HEIC in Chrome) says "Vali JPG või PNG pilt"; one over 60 MB is refused before it is opened.
   - **On the server:** it takes only a JPEG (the first bytes are checked) of at most 2 MB and 1–4096 px a side, with a thumbnail of at most 200 KB. A request over the sum plus 64 KiB is refused before it is read (Vercel refuses bodies over 4.5 MB itself).
   - **Rate limits:** at most 120 photo uploads in each clock hour per student (a fixed window: steady work through a long course starts again each hour), 20 sends an hour; 10 test submits (and rewrites) an hour.
   - **Storage:** R2 holds the photos privately, never served by `/media`. A photo that cannot be stored (the four `R2_*` variables are missing, or R2 refuses) answers 503 "storage", the files already written are removed again, and the student's page offers "Proovi uuesti".
5. **The mails.** All go after the commit, never undo what was saved, carry a link and the names of the course and the student but never an answer, a note or a photo, and skip sample addresses.
   - **To the student, in her language:** "Sinu praktiline töö on hinnatud" (with how many "Paranda" points, when there are any), "Palju õnne! Koolitus „…“ on lõpetatud", "Test on sooritatud" (Maria accepted the open answers and the practical work is next), "Vaata üle oma testi vastused", "Test on sinu jaoks uuesti avatud", and, for an e-course without points, the protocol mails "Sinu koolituse protokoll on valmis" and "Sinu koolituse protokolli on uuendatud". The three test mails (the pass, the rewrite request, the reopening) and "Sinu praktiline töö on hinnatud" are not sent to an expired access (item 3).
   - **To Maria, by mail and Telegram:** "Praktiline töö hindamiseks: {nimi}, {kursus}" ("(2. kord)" on a later round), "Test ootab hindamist: …", "Testi katsed otsas: …". They are sent for a sample student too, as her live check needs.
   - **Reply-To:** every mail without its own Reply-To has `MARIA_EMAIL`, so a student's reply reaches Maria. The exception is a mail to Maria herself; her notices reply to the student.
6. **The logs.** A failure is written at error level; where an error caused it, `<error class>` is the class, the code and the HTTP status only (section 12, item 7).
   - **The test:** `[test] attempt N: submitted (failed|review|passed)`, `[test] attempt N: rewritten (review)`, `[test] attempt N: reviewed (passed|fix)`, `[test] attempt N: Maria notified by e-mail: …, Telegram: …`, `[test] access N: reopened`; failures `[test] attempt N: the review failed: <error class>` and `[test] access N: the reopen failed: <error class>`.
   - **The practical work:** `[practical] access N: submitted (round R)`, `[practical] access N: Maria notified by e-mail: …, Telegram: …`; `[practical] access N: a photo could not be stored: <error class>`, `[practical] access N: a photo refused, no file store (…)` (it names the four `R2_*` variables), `[practical] access N: a photo file could not be removed: <error class>` and `[practical] access N: no file store, K photo files not removed` (or `[practical] client N: …` for the same two after an account's deletion); `[practical] photo N: the admin's read failed: <error class>`.
   - **The assessment:** `[assessment] access N: sent (fix)`, `sent (passed)` or `sent (passed, completed)` (and `sent (open)` for the notes of an e-course without points); failures `[assessment] access N: the verdict failed: <error class>` and `[assessment] access N: the send failed: <error class>`; the notes' autosave and re-read on an access: `[protocols] access N: the save failed: <error class>` and `[protocols] access N: the screen could not be read: <error class>`.
   - **The completion:** `[completion] access N: completed`, `[completion] access N: the check failed: <error class>`, `[completion] access N: the <kind> mail sent` (or `the <kind> mail was not sent`, `the <kind> mail failed: <error class>`; the kinds are assessed, completed, testPassed, testFix, reopened, protocol and protocolAgain). A task after the answer that threw outside its own catch is `[account] background task failed: <error class>` (the student's side), or `[test] a mail failed: <error class>` and `[assessment] a mail failed: <error class>` (Maria's actions).
   - **The limits:** `[account] test submits rate limited`, `[account] photo uploads rate limited` and `[account] practical submits rate limited`.
   - Never an answer, a note, a name, an address or an R2 key.
7. **Rollback.** A rollback of the code past this phase leaves 0008's additions in place, and the older code ignores them. It has no test or practical pages: a mail's link lands on a 404 until the code is back.
   - **Account deletion:** the older code does not remove the R2 photos. They are deleted with the database rows, but their objects stay in the bucket. Delete them by hand afterwards: the keys are under `practical/` and no longer named by any `practical_photos` row.
   - **The test:** the older course editor does not show "Teadmiste test", and saving a course there leaves `course_tests` as it was.
   - **The practical points:** the older course editor saves an e-course with `protocol_stages = []`, which wipes its practical points. The protocols that exist keep their own copy, but a new student would get none (no practical step, and her course completes without it). Do not save e-courses while rolled back; if one was saved, enter its "Protokolli punktid" again once the code is back.

## 14. The e-course certificate

When an e-course is "Lõpetatud", the student confirms her name once and downloads a PDF certificate that looks like Maria's paper ones and continues their number series (spec `docs/superpowers/specs/2026-10-15-certificate-design.md`, plan `docs/superpowers/plans/2026-10-15-certificate.md`). E-courses only: contact courses stay on paper.

1. **What runs where.**
   - **The student:** the "Tunnistus" row of "Lõpetamine" on `/konto/kursus/<slug>` ("Nimi tunnistusel", "Kinnita ja koosta tunnistus", then "Laadi tunnistus alla (PDF)"), and the quiet link "Laadi tunnistus alla" on the dashboard card of an ended access; an ended access completed without a certificate yet has the same name form on its card instead (the course page needs an active access). Her routes are `POST /api/konto/kursus/<slug>/tunnistus` (`{ name }`) and `GET /api/konto/tunnistus/<id>` (the PDF): `private, no-store`, at most 10 issues and 10 downloads an hour per student, and behind the coming-soon gate until the launch, like every account route.
   - **Maria's pages:** the course editor's "Tunnistus" card on e-courses ("Oskused tunnistusel", "Maht"); Seaded → "Tunnistus" (a card of its own under the settings' save bar: "Koht", "Registrikood", "Praktilise töö rida", "Koolitaja nimi" — her signature —, "Järgmine number" with the year's last issued number); the Õpilased drawer's line "Tunnistus MS LAB 2026-03 · {date}" with "Laada alla" and "Paranda nimi"; the register `/admin/tunnistused` (Hindamine's second tab „Tunnistused“, which both pages show; not in the menu; 50 a page, newest first).
   - **Maria's endpoint:** `GET /api/admin/tunnistus/<id>` (any certificate, a revoked access's too), behind `withAdmin`, `maxDuration = 30`. The settings' save and "Paranda nimi" are server actions (`src/server/actions/admin-certificates.ts`).
   - **Configuration:** no new variable, no cron, nothing in R2. The fonts are files of the repository (`app/assets/fonts/`: Jost with its OFL text, and Revive 80 Signature, checked by SHA-256 in the tests); `next.config.ts` traces them into the two functions that render (`outputFileTracingIncludes` keys `/api/konto/**` and `/api/admin/tunnistus/**`, the folders of `/api/konto/[[...path]]` and `/api/admin/tunnistus/[id]`; bracketed keys trace nothing under Turbopack). The only new packages are `pdf-lib@1.17.1` and `@pdf-lib/fontkit@1.1.1`, pinned exactly.
   - **The script font's licence:** `Revive80Signature.otf` is Maria's Canva font Revive 80 Signature (© Tom Chalky / Inspiration Hut), licensed to MS LAB for its certificates. It is not open source: it is never copied out of `app/assets/fonts/` or attached anywhere else. The repository may stay public: Dim, the owner, confirmed on 15.10.2026 that MS LAB has the approval of Canva and Tom Chalky and waived the private-repository gate that this runbook first had.
2. **The data.** Migration `0009_certificates` is additive. It runs on Railway before the deploy (section 6), and the live code does not name what it adds.
   - `certificates`: one row per completed access (unique `access_id`, deleted with the access and so with the account), the number "MS LAB {year}-{nn}" with `year` and `seq` (unique together, `seq` ≥ 1), and the frozen copy: the name as confirmed, the course's Estonian title, the skills, the volume, the practical line, the place, the registry code and `issued_at` (the date printed); `reissued_at` after "Paranda nimi".
   - `courses.certificate_skills` (jsonb lines, `[]`) and `courses.certificate_volume` (text, `''`): the course editor's card. With no lines, the course's "Õpiväljundid" (Estonian) are printed, at most 16; the card warns when one of them is over 120 characters (it would not fit), and cuts nothing.
   - The `settings` row `certificate`: `{ place, registryCode, practicalLine, trainerName, nextYear, nextSeq }`. Without it, the defaults: Pärnu linn, 16346048, the plan's practical line, Maria Sosnina, this year, 1. A stored `trainerName` the name rules refuse reads as Maria Sosnina.
   - The drop of `courses.modules` is migration 0010 (code first, then the migration, as planned in phase 3a).
3. **The rules.**
   - **Numbering:** a certificate issued in Tallinn year Y takes the setting's `nextSeq` when its `nextYear` is Y, else 1, **and never less than year Y's highest issued number + 1**; the setting then becomes Y and the number after the one used. This is `seqToIssue` in `src/domain/certificate.ts`, the one rule that the issue and Seaded's card call; Seaded's "taken" check reads the same highest number. The floor is there so that a setting saved for another year, or a lost setting row, can never stall the series: the unique (`year`, `seq`) would refuse every later issue otherwise. A number ahead of the highest (Maria's jump) is kept. So Seaded's card shows the number the next issue will actually take: in January, this year's number while the stored year is still last year's; a setting for a later year (a December preset) is shown as she saved it. The year turns at Tallinn midnight on 31.12. The issue runs in one transaction: the access row (`FOR UPDATE`), then the refusals (a revoked access is "not found", one not completed "not completed", one with a certificate answers "already" with it), then the transaction's advisory lock `pg_advisory_xact_lock(hashtext('certificate-number'))`, then the setting is read and advanced and the row written; the unique (`year`, `seq`) is the backstop. Two students at the same moment get two numbers, one after the other; one student on two devices gets one certificate, and the second answer is "already" with the same number (`tests/e2e/certificate-race.spec.ts`). Seaded's save takes the same lock before it rewrites the setting.
   - **One series with paper:** Maria's paper certificates (contact courses) share the series. When she writes one on paper, she takes the number Seaded shows as next and raises "Järgmine number" by one ("Salvesta tunnistuse andmed"); otherwise the site can issue the same number. Seaded refuses a next number at or below one already issued in its year ("See number on juba väljastatud. …") and a year other than this Tallinn year or the next ("Aasta peab olema käesolev või järgmine."): an issue never uses a past year's setting, so her number for it would be lost.
   - **The frozen copy:** a certificate prints only what its row holds. A later change of the course (its title, its card) or of Seaded's place, registry code or practical line never changes an issued certificate. The one thing read at each download is "Koolitaja nimi", Maria's signature (a new one appears on every later download, old certificates included).
   - **The name:** NFC, trimmed, inner spaces collapsed; 2–80 characters with at least 2 letters; the Latin letters the script font draws (`A–Z a–z À–Ö Ø–ï ñ–ö ø–ý ÿ ı Œ œ Š š Ÿ Ž ž`: Estonian, Finnish, German, French, Scandinavian, Spanish, Portuguese, Italian), spaces, hyphens, apostrophes (' and ’) and dots. The student writes her name in Latin letters as in her passport: Cyrillic is refused, and so are Č, Ł, Ā, Ę and the like, digits and emoji, with "Kirjuta nimi ladina tähtedega nagu passis (lubatud on ka tühik, sidekriips ja ülakoma)." (in Russian: "Напишите имя латинскими буквами, как в паспорте (можно также пробел, дефис и апостроф).") before anything is stored. "Koolitaja nimi" in Seaded follows the same rules. A long name shrinks on the PDF, then wraps to two lines.
   - **Who may download:** the student her own certificate while her access is not revoked (expiry does not matter); a revoked access answers 404, and its card link goes. Maria every certificate, a revoked access's too, marked "ligipääs tühistatud" in the drawer and the register.
   - **"Paranda nimi":** the student's rules; it keeps the number and the issue date, changes the name and sets `reissued_at`, and mails nobody. The student cannot change her name once it is issued: her row says "Kui nimes on viga, kirjuta meile".
   - **Deletion:** the account's deletion takes its certificates (cascade); their numbers are not reused, so the series has a gap.
4. **The PDF.** Rendered on every download from the frozen row (`src/server/certificate-pdf.ts`): A4 landscape (842 × 595 pt), black, white text, the MS LAB logo drawn as vector shapes, the student's name and "Koolitaja nimi" (the signature, bottom right above "KOOLITAJA") in Revive 80 Signature; about a tenth of a second, under 300 KB (about 160–180 KB). Jost is embedded as a subset and Revive 80 Signature whole: pdf-lib 1.17.1 with @pdf-lib/fontkit 1.1.1 subsets this CFF font into a file PDF viewers reject (MuPDF: "unknown file format"), and the whole font renders correctly. Nothing is stored. The answer is `attachment; filename="MS-LAB-tunnistus-{year}-{nn}.pdf"`, `private, no-store`, nosniff (Maria's `/api/admin/…` answers get `Cache-Control: no-store` from `next.config.ts`). A function log saying a font is missing (`ENOENT … assets/fonts`) means the tracing of `next.config.ts` did not include it: check the deployment's function files.
5. **The signature.** Maria's signature is her name typed in Revive 80 Signature, as on her Canva certificates: Seaded → Tunnistus → "Koolitaja nimi" (default "Maria Sosnina"), written as she wants it signed, in Latin letters. There is no picture to upload and none is stored anywhere. A changed name appears on every later download, old certificates included.
6. **The mails.** The "Palju õnne!" mail of a completed e-course has one more line, "Kinnita oma nimi ja laadi tunnistus alla:", with the course page's link, or the dashboard's (`/konto`) when the access is no longer active as the mail is built (Maria approved after it ended: its card has the form); no attachment. For a course without points the button opens that same course page, so the line stands above the button and the address is written once. Nothing else mails: the issue and "Paranda nimi" send nothing.
7. **The logs.** A failure is written at error level; `<error class>` is the class, the code and the HTTP status only (section 12, item 7).
   - **The issue:** `[certificate] access N: issued <number>`, `[certificate] N: re-issued`; failure `[certificate] N: the re-issue failed: <error class>`.
   - **The student's routes:** `[account] certificate issues rate limited` and `[account] certificate downloads rate limited` (10 an hour each, per student); a render that fails `[certificate] N: the student's download failed: <error class>`; anything else that throws in them is the account API's general `[account] request failed: <error class>`.
   - **Maria's download and the settings:** `[certificate] N: the admin's download failed: <error class>`, `[certificate] the settings save failed: <error class>`.
   - Never a name or an address.
8. **Rollback.** A rollback of the code past this phase leaves 0009's additions in place, and the older code ignores them: the student's routes, the "Tunnistus" row and the register are gone (the completed mail's link lands on her course page without the row), and no certificate can be downloaded until the code is back. The older course editor saves a course without touching its two certificate columns.
9. **Deploying** (this phase's go-live, and every push after it), in this order:
   1. **The font's licence.** Nothing to check before a push: the owner waived the private-repository gate on 15.10.2026 (item 1, "The script font's licence").
   2. Migration 0009 on Railway (section 6: the count goes from 9 to 10).
   3. The test plan's stamp: `node tools/testplan-stamp.mjs` from `app/`, committed with the merge (section 15).
   4. The push of `main` (Vercel deploys it).
   5. The smoke check: `/api/admin/tunnistus/1` answers 401 without a session.

## 15. Testimine (the test page)

The acceptance walk of the site, written down (phase 4 piece 1, spec `docs/superpowers/specs/2026-10-16-test-page-design.md`): `/admin/testimine`, titled "Testimine", where Maria and Dim tick each check "OK", "Viga" or "Jäta vahele" with a note, and see each other's answers. It is for the two admins only, and since the admin UX pass (section 20) it has its own entry, „Testimine“, in the menu for every admin (spec Q5; the number on it is the admin's own failed checks); the overview (Avaleht) also shows a card "Testimine: N avatud, M viga" with the open and failed checks of the admin's own `who` (Maria: `maria` + `koos`; Dim: `dim` + `koos`; matched by the first word of the name in `ADMIN_NAMES`), and only while there are some. The card goes away by itself once none of that admin's checks is open or failed.

1. **What runs where.**
   - **The plan** is the committed file `app/src/data/testplan.json`: the areas in their order and the checks (steps, what to see, why, `who`, the device, whether running it creates data). `tests/unit/testplan-file.test.ts` holds it to `checkPlan` (`src/domain/testplan.ts`), the house style: at most 8 steps and 8 expect lines, at most 20 words a line, every line a sentence with a full stop, known ids and enums, no free-mail address. The checks' buttons and labels are the screen's words, in „…“.
   - **The page** loads the plan and the answers in one call, `GET /api/admin/testplan`. A press saves at once and a note 1 s after typing stops (and when the field loses focus), through `PUT /api/admin/testplan`. Both are behind `withAdmin`, never cached; a save body is at most 128 KB and a note 1 000 characters. Unsent answers wait in the device's storage and go when the connection is back ("Salvestamata — proovin uuesti"). When the answers cannot be read (the database is down) and nothing is waiting, the page says "Vastuseid ei saa praegu salvestada; need on selles seadmes alles." A device that cannot keep an answer (no storage, or one that refused the last press: blocked or full) does not say it: there an unsent answer lives in the open page only, and the page shows just "Salvestan…" and "Salvestamata — proovin uuesti". A press the server has confirmed leaves the storage at once, also when the page was left while its save was on its way, so a later visit never sends it again over a newer answer.
   - **Configuration:** no migration, no variable, no cron. The build instant is inlined by `next.config.ts` as `TESTPLAN_BUILD_AT`; it is not a configured variable (section 2 does not list it).
2. **The answers row.** One `settings` row, key `testplan_answers`: `{ v: 1, answers: { <check id>: { status, note, at, by, pinged?, notePinged? } } }`, and since 25.10 an optional `auto` of the same shape, Automaattest's answers (item 7).
   - `at` (and `pinged`) are the server's clock at the save, never the device's; `by` is the session's e-mail address and never leaves the server (the page shows the first name of `ADMIN_NAMES`).
   - A save merges by check id under the row's lock (`select … for update`, the row inserted first when missing): the newer `at` wins, and two saves at once both survive. Reading creates no row.
   - Answers to ids no longer in the plan stay in the row and are never shown.
   - To start the answers over (for example after the launch), delete the row on Railway (section 6; read it first). That throws away every answer.
3. **The plan follows the code (the standing rule, spec §6).** Every later change that alters what a check describes updates `testplan.json` in the same commit:
   - `"mark": "redo"` when the site behaves differently: the check opens again for whoever answered it, with the old answer under it ("Varasem vastus (enne muudatust): …"). `"mark": "reworded"` when only the words move; a new check with `"mark": "new"` for new behaviour. A fix for a "Viga" marks that check `redo` in the same commit. A behaviour that shows only on particular data gets a new check naming that data: a `redo` alone is not coverage.
   - **On a branch**, a marked check carries `"markedAt": "deploy"`: a branch can wait for days, and an answer given meanwhile was about the old site.
   - **Right before every push to `main`**, from `app/`: `node tools/testplan-stamp.mjs`. It replaces every `"markedAt": "deploy"` with the current instant (a text replacement: nothing else in the file changes) and prints how many it replaced; with none, the file is left untouched. Commit the result with the merge. The deploy follows within minutes.
   - **The safety net:** a `"deploy"` that reaches a deployment unstamped reads as that build's instant (`TESTPLAN_BUILD_AT`). The check opens again at that deploy, as it should, and again at every later deploy until the tool stamps it. That asks too much rather than too little, and never hides a change.
   - Never move the plan-wide `"marked"` to cover one check: it would open other checks' answers again.
   - **Ids never change.** The answers hang on the id: a renamed id loses its answer, and no test can catch that. A changed meaning is a mark, not a new id.
4. **The Telegram messages** (spec D6). Through the existing chat (`sendTelegram`: the review tools' chat, Dim's until the launch, `docs/launch-checklist.md` section 1), after the answer has gone:
   - when a check becomes Viga: "Testimine — Viga: {title} ({name})", the note's first 300 characters or "(märkust veel pole)", and the link `<site>/admin/testimine#<id>`;
   - once, when that Viga gets its first note: "Testimine — Märkus: {title} ({name}) · Viga", the note's first 300 characters and the link;
   - **since 22.10 (Dim: every answer has a note box)** the same message goes out once for the first note on an "OK" or a "Jäta vahele" too, with the answer at the end: "Testimine — Märkus: {title} ({name}) · OK" or "· Jäta vahele" (a check answered without a note sends nothing);
   - nothing more for the same answer: later edits of the note send nothing. A Viga on a check that a `redo` opened again is a new failure and sends its own messages (a fix did not work); an OK or a "Jäta vahele" given after a `redo` is a new answer too, with its own first note.
   - A press carries the check's note as it stands, so a Viga pressed on an OK or a "Jäta vahele" with a note carries that old note along. It is not the failure's: the first message says "(märkust veel pole)", and the note typed next goes as the second message. The same holds when the answer changes to an OK or a "Jäta vahele": the note it carries is not its own, so only a note typed after the press sends a message.
   - A failed send never fails the save. The message is recorded as sent when the save is stored, so a send that fails is logged (with the check's id) and not tried again: read the page.
5. **The logs.** `[testplan] saved N answers, N messages`, `[testplan] a Telegram message failed (check <id>)`, `[testplan] the answers could not be read: <error class>` and `[testplan] the save failed: <error class>`. Ids and counts only: never a note, an e-mail address or a name.
6. **The test data** (spec D7). The checks name everything they create "Proov" and a number, and a student's address is the tester's own with `+proov<n>` before the @ (one per role, as the plan's "Enne alustamist" says). The test rows stay in the database, labelled, while testing goes on. The testers write every address they used into the check `koristamine-aadressid`; before the public launch Dim removes those rows by exact address (`docs/launch-checklist.md` section 14).
7. **Automaattest, a third tester (Dim 25.10, spec D10).** An automatic tester may run the plan's checks on mslab.ee. Its answers are kept apart and never count as Maria's or Dim's.
   - **What Dim sets in Vercel** (no address goes into the repository): the tester's address added to `ADMIN_EMAILS`, and `<address>=Automaattest` added to `ADMIN_NAMES` (a name that starts with „Automaattest“, in any case); then redeploy, so the new values reach the functions. Set both before its first run: while its address has no such name it is an ordinary admin, and its answers land in the shared `answers`. It signs in with the ordinary magic link. The admin guards are unchanged: it is an admin like the others and can do whatever an admin can.
   - **Its answers** go into the same row's own map `auto` (item 2), saved under the same lock: its saves never write `answers`, and Maria's and Dim's never write `auto`. No migration; a row without `auto` reads as before.
   - **What Maria and Dim see:** their own answers and numbers exactly as before (the header, the areas' counts, the Avaleht card, the menu badge). Under each check Automaattest answered, one quiet line „Automaattest: OK · dd.mm HH:MM“ (or „Viga“, „Jäta vahele“; „Automaattest: Varasem vastus (enne muudatust): …“ once a `redo` has overtaken it), with its note under it. The „Kes“ row has „Automaattest“: the checks it answered. Its own session sees every check, with its own answers, card and badge.
   - **Telegram:** its Viga sends the first message, and that Viga's first note the second, as in item 4 with „(Automaattest)“ as the name. Its „OK“ and „Jäta vahele“ send nothing, with a note or without.
   - **Rollback** to code from before 25.10: the older code reads the row and ignores `auto`, so Maria's and Dim's answers are untouched; but its first save writes the row back without `auto` (Automaattest's answers are gone), and it takes Automaattest for an ordinary admin, whose saves would land in the shared `answers` as if Maria's or Dim's. So before rolling back, stop the automatic tester and take its address out of `ADMIN_EMAILS` (redeploy); to keep its answers, read the row on Railway first (section 6) and keep a copy of `auto`.
   - **To clear its answers only** (Railway, section 6; read the row first): `UPDATE settings SET value = value - 'auto' WHERE key = 'testplan_answers';`.

## 16. Invoices („Arved“)

The site makes the invoices itself and Maria's accountant gets one file a month (phase 4, piece 2, spec `docs/superpowers/specs/2026-10-16-invoices-design.md`, plan `docs/superpowers/plans/2026-10-16-invoices.md`; where the build departed from the spec, the spec says "amended 16.10 during the build"). Every euro a student pays has a numbered invoice; she finds it in her account and, if Maria sends it, in her mailbox.

1. **What runs where.**
   - **Maria's screens:** the registration drawer's block „Arved“ (Registreerimised → the registration: its invoices, „Koosta arve“, and on an invoice „Saada õpilasele“ and „Laadi alla (PDF)“ in sight, „Muuda saajat“, „Märgi tasutuks“, „Võta tasumine tagasi“ and „Tühista arve“ under „Veel ▾“); the page `/admin/arved` (the second tab of Maksed, not in the menu: all invoices newest first, 50 a page, a search over number, name and e-mail, a month select that applies on change, filters by state, the strip „Arveta maksed: {n}“ on top while there are any, „Laadi alla (CSV) · {kuu aasta}“; admin UX pass, piece 2: section 22, item 3); Seaded → „Arve andmed“ with „Näidisarve (PDF)“.
   - **Routes:** `GET /api/admin/arve/<id>` (any invoice's PDF), `GET /api/admin/arved?kuu=YYYY-MM` (the month's CSV) and `GET /api/admin/naidisarve` (the sample, drawn from the values on Seaded's card, stored nowhere), all behind `withAdmin`; the student's `GET /api/konto/arve/<id>` (item 11). Every PDF and CSV answer is `private, no-store` with `x-content-type-options: nosniff` (`next.config.ts` sets the first for the three admin routes). The buttons are server actions (`src/server/actions/admin-invoices.ts`, `adminAction`).
   - **The code:** `src/domain/invoice.ts` (the rules without a database: numbers, VAT, the open amounts, the CSV), `src/server/invoices.ts` (everything that writes or reads invoices), `src/server/invoice-pdf.ts` (the PDF), `src/server/invoice-send.ts` (Maria's mail).
   - **Configuration:** no new variable, no cron, nothing in R2, no new package or font (Jost and pdf-lib are the certificate's, section 14). pdf-lib is loaded only when a PDF is drawn. `next.config.ts` traces `./assets/fonts/**` into every function that can draw an invoice: the account API, Maria's download and the sample, `/api/payments/**` and `/api/cron/**` (a settlement's paid mail carries the PDF) and `/admin/**` (the pages whose actions send it). A function log saying `ENOENT … assets/fonts` means the tracing missed one.
2. **The data.** Migration `0011_invoices` is additive: the table `invoices` and the column `payments.invoice_id`. Migration `0012_invoice_footer` (the final review's wave) is additive too: `invoices.footer` (text, not null, default empty: the footer line frozen at the issue, item 4) and the index `payments_invoice` on `payments.invoice_id` (the „paid online“ read of item 7 per invoice row, and the set null of an invoice's deletion). Both run on Railway before the deploy (section 6), together, and the live code names nothing they add.
   - An invoice holds its number (`number`, `prefix`, `year`, `seq`), `kind` (`prepayment`, `full`, `balance`, `ecourse`), `status` (`unpaid`, `paid`, `cancelled`), `amount_cents` (the gross sum, above 0), `vat_rate` (null when VAT was off), the frozen copies `line`, `seller` and `buyer` (jsonb), the payment `reference`, `issued_at`, `due_at`, `paid_at`, `paid_method` (`montonio`, `bank`, `cash`, `card`), `paid_adds`, `sent_at`, `sent_note`, `cancelled_at` and (0012) `footer`.
   - Links: `registration_id`, `course_id`, `client_id` and `payment_id`, each set to null when its row is deleted: an invoice outlives a registration, a course and an account (the buyer is frozen on it). `payment_id` is unique: a payment is named by at most one invoice. `number` and (`prefix`, `year`, `seq`) are unique. `payments.invoice_id` is the invoice a payment was started to pay (item 7).
   - The `settings` row `invoice`: `{ company, registryCode, address, vatNumber, vatOn, vatRate, prefix, nextYear, nextSeq, termDays, footer }` (Seaded → „Arve andmed“); defaults: empty texts, prefix `MSL`, VAT off at 24, a week to pay, this year from 1. The bank account is not here: the receiver, the IBAN and the bank are read from Ettemaksu juhised (the `prepayment` row) when an invoice is made.
3. **The numbers and the lock order.**
   - **The number** is `{prefix}{year}-{nnn}` (`MSL2026-001`; three digits at least, it grows past 999), the year being the Tallinn year of the issue. A seq is never below that prefix-year's highest + 1 (`invoiceSeq`, the certificate's `seqToIssue` rule, section 14 item 3), so a setting saved for another year, or a lost one, cannot stall the series. A cancelled invoice keeps its number.
   - **Each prefix has its own series**. Saving Seaded with a different prefix sets „Järgmine number“ back to 1 (the setting holds one counter; the highest-plus-one rule then continues every prefix's own series: a new prefix starts at 001, going back to an old one continues after its highest). With the same prefix Seaded refuses a next number at or below the highest issued ("taken"). The card shows the number the next issue will take, and the last one issued beside it. The year turns at Tallinn midnight on 31.12.
   - **The locks**, always in this order, so no two writes wait for each other the other way round: (1) `lockForPayment` (the session, then the registration) when a registration is involved; (2) the payment row or the invoice row, `FOR UPDATE`; (3) the transaction lock `pg_advisory_xact_lock(hashtext('invoice-number'))`; (4) the `invoice` setting. Every issue holds 3 and 4 in one transaction; Seaded's save takes 3 as well. Maria's actions and a settlement take 1 and 2 in the same order, so a „Märgi tasutuks“ and a payment of the same invoice at the same moment wait on the same session-row lock: one goes first and the other then finds its result. The invoice is paid once; a second real payment gets an invoice of its own and both amounts are counted (item 7, ruling R7). Two issues on two registrations at the same moment wait on lock 3: the second reads the first's committed number, so they take consecutive numbers, never one twice. All of this is pinned on real Postgres by `tests/e2e/invoices-race.spec.ts`. The one pair that can still deadlock in theory is the catch-up of a payment against the deletion of the same student's account (accepted); Postgres then ends one of them, and trying again works.
4. **The seller copy.** Each invoice copies, when it is made, the company, registry code, address and VAT number of „Arve andmed“, the receiver, IBAN and bank of Ettemaksu juhised, the VAT rate (none when VAT is off), its line (the course's Estonian title, the session's date and city, the part: „Ettemaks 50%“, „Kogu summa (100%)“, „Jääk 50%“, „Osamakse“ for an amount that is none of them (item 6), or the e-course) and its buyer (the registration's or the payment's name and e-mail). A later change of company, VAT, IBAN, prefix or price never alters an issued invoice. The optional footer line of „Arve andmed“ is frozen on the invoice too (`invoices.footer`, migration 0012, the final review's I2): its PDF always prints the line of its issue, whatever Seaded says on the day of a download. The invoices issued before 0012 have none. One thing is not frozen: the buyer of an **unpaid** invoice, which Maria may change („Muuda saajat“: the name, an address, and a company with its registry code and address for a student whose company pays; once paid, it is frozen).
5. **VAT on and off.** Off is the default and the safe state: no VAT lines, the PDF's footer „Arve ei sisalda käibemaksu (müüja ei ole käibemaksukohustuslane).“, and the KMKR number is not printed. On needs the KMKR number (Seaded refuses „Käibemaksuga arve vajab KMKR numbrit.“; a stored card with VAT on and no number reads as off) and a whole rate of 1–50 (default 24, Estonia's standard rate since 1.7.2025). Course prices already contain VAT: `vat = round(gross × rate / (100 + rate))`, `net = gross − vat`, in cents, and the PDF shows „Summa käibemaksuta“, „Käibemaks {rate}%“ and „Kokku“. The rate is frozen on each invoice, so turning VAT on or off changes only the invoices made afterwards. Whether the academy is VAT-registered is not settled (Dim, 16.10.2026): leave it off until Maria's accountant says otherwise, and have the accountant check one sample invoice (`docs/launch-checklist.md` section 15).
6. **How Maria makes and changes an invoice.**
   - **Without a seller there is no invoice** (D3). Until „Arve andmed“ has a company, a registry code and an address, „Koosta arve“ is a link to Seaded, and a paid online payment is recorded without an invoice (item 8).
   - **„Koosta arve“** offers only the amounts still open: the registration's price less its unpaid and paid invoices (a cancelled one is open again) and less its paid online payments that have no invoice yet (the final review's I1: their money is in „Laekunud summa“ already). „Ettemaks 50%“ and „Kogu summa (100%)“ exclude each other, and the rest is offered once something is covered but not all. It also works on a cancelled registration, whose unpaid invoice stays until Maria cancels it.
   - **The block lists those payments.** A paid online payment of the registration with no invoice yet (it is also in „Arveta maksed“, item 8) is listed on the block, „Veebimakse {summa} ({kuupäev}) on veel arveta.“, with its own „Koosta arve“: the catch-up of item 8, which pays the invoice it was started for or makes its own.
   - **Money typed by hand.** When „Laekunud summa“ holds more than the paid invoices cover (a transfer recorded by hand with „Lisa laekumine“, m4), „Maksmiseks“ never asks for that money again (it offers the rest only), and „Juba tasutud“ offers exactly that recorded, uncovered money and nothing else (admin UX pass, piece 2, B4: with nothing uncovered the kind cannot be chosen and the server refuses a higher amount, so a receipt for venue money that was never recorded is made by „Lisa laekumine“ with the receipt box ticked, section 22, item 4): as „Ettemaks 50%“, „Kogu summa (100%)“ or „Jääk 50%“ when it is that part, else „Osamakse“. A part that is no half, whole sum or rest is „Osamakse“ on an online payment's invoice too (m10: a whole-sum registration's rest paid online after a part recorded by hand). A kind with nothing to offer cannot be chosen. Two kinds:
     - **„Maksmiseks“:** an unpaid invoice („Tasumata“) due in Seaded's term (a week), with the bank details of Ettemaksu juhised and the payment reference (`{referencePrefix}{registration id}`, as the account shows it). It needs the receiver and the IBAN there: without them „Koosta arve“ refuses and says to fill Ettemaksu juhised first. It is in the student's account at once.
     - **„Juba tasutud“:** a receipt for money already received, born paid on the day (not after today in Tallinn) and the way she gives: „Pangaülekanne“, „Sularaha“ or „Kaardimakse kohapeal“. It does not touch „Laekunud summa“, which already holds the money (a receipt that „Lisa laekumine“ makes is the other way round: it adds the money in the same step).
   - **„Märgi tasutuks“** on a request (the date, default today, and the way) adds its amount to the registration's „Laekunud summa“ in the same transaction, and the registration confirms from 50 % as it does for any payment (when the session is full it stays unconfirmed and the screen says so). Money that has no invoice is recorded with „Lisa laekumine“ (the typed field and „Salvesta summa“ are gone, section 22, item 4). An invoice whose registration is gone is paid and adds nothing.
   - **„Võta tasumine tagasi“** asks first. A **request** goes back to unpaid, its date and way cleared, and its amount comes off „Laekunud summa“ (the status is worked out again: the place stays while the rest is still 50 %). A **receipt** (born paid, no due date) is **cancelled** instead and keeps its number (amended in the spec, D6): back to unpaid it would be a payable invoice for money already received, and its „Märgi tasutuks“ would count that money twice. Since the admin UX pass, piece 2 (B4) its amount comes off „Laekunud summa“ as well, capped and never confirming a seat (section 22, item 4; this replaces ruling R10, under which „Laekunud summa“ stayed), and the amount is open again for the right receipt. An invoice paid by Montonio is never changed by the site (nor by an undo).
   - **„Tühista arve“** asks first, works on an unpaid invoice only and keeps its number; its amount is open again. A paid invoice is never cancelled: Maria undoes the mark first.
   - Two marks, or a mark and a cancel, at the same moment: the second finds the invoice changed and is refused (`notUnpaid`), so the amount is added once.
7. **Online payments and their invoices.**
   - **The payment link.** `payments.invoice_id` is the unpaid invoice a payment was started to pay: while a registration has an unpaid invoice, „Maksa“ (the pay page and the account's button) charges exactly that invoice's amount, the course day too, and the Montonio payment is started for it. `invoices.payment_id` is the payment an invoice was paid by. A payment is **invoiced** exactly when an invoice has its `payment_id`: the invoice it was started for (paid by Montonio, on the payment's time, `paid_adds` false because the payment adds its own amount), or one born paid for it (its kind from the payment: the prepayment, the whole sum of a registration that chose to pay it all, the rest, or the e-course).
   - **Once, in the winner's transaction.** The one door of every paid path (`settlePayment`, section 11) calls `invoiceForPaidPayment` once, from the call that wins the pending → paid update, inside the same transaction and after its own locks. The webhook, the return and the daily check therefore never make two. Idempotent: a call again returns the invoice the first gave.
   - **The savepoint** (amended in the spec, D5): the invoice step runs in a **savepoint** of the paid transaction. Whatever it throws, only the invoice is rolled back: the payment stays paid, the amount is on the registration and the e-course is open, as before invoices existed. It is logged `[invoices] payment N: no invoice: <class>` (error level), the payer's mail goes without the PDF and without „Arve on lisatud.“, and the payment waits in „Arveta maksed“ for its catch-up (item 8). (A lost connection still fails the whole transaction and leaves the payment pending for the next call, as before.)
   - **A failed invoice is not payable twice**. While a paid payment started for invoice X exists, has no invoice of its own (no invoice names it as its payment) and X still reads unpaid (the step failed), X is not charged again and „Märgi tasutuks“ refuses it ("See arve on juba veebis tasutud — koosta arve „Arveta maksed“ alt.") until the catch-up pays X. Maria's row of X says „Veebis tasutud — ootab „Arveta maksed“ alt arvet.“ and has no „Saada õpilasele“ and no „Märgi tasutuks“ (m2). A payment that has an invoice of its own (R7: Maria marked X meanwhile, then undid her mark) leaves X an ordinary unpaid invoice (m1).
   - **Maria's mark against a payment**. If the invoice a payment was started for is no longer unpaid when the payment settles (Maria marked or cancelled it meanwhile), the payment's money gets an invoice of its own, born paid, of that invoice's part: two real payments are two invoices, „Laekunud summa“ counts both, and the usual „Ülemakse“ alert tells Maria when the sum is over the price; she refunds the extra in Montonio. Whichever of the two comes first, the invoice is paid once and nothing is left unpaid and charged (pinned on real Postgres by `tests/e2e/invoices-race.spec.ts`).
   - **„Tagastatud“.** A refunded or voided payment (refunded, or failed with its `paid_at`) keeps its invoice. That invoice reads „Tagastatud“ on Maria's list and block, on the student's card and in the CSV's state column (the final review's I3, amended in the spec, D5). It stays stored paid, its sums as issued (the „Tasutud“ filter of the list finds it). Credit notes are out of scope, and Maria handles the accounting.
8. **„Arveta maksed“ (the catch-up).** A paid payment that no invoice names: paid while Seaded's seller was empty, or whose invoice step failed (item 7). They are listed at the top of `/admin/arved`, oldest first, each with its own „Koosta arve“ and, in the strip above them, „Koosta {n} arvet“ for all of them (admin UX pass B11: still one catch-up and one number per payment, oldest first; one that fails is named and does not stop the rest), and a registration's own on its block (item 6). A payment started for an invoice that is still unpaid pays **that** invoice; otherwise one is issued now (today's date, the next number), born paid on the payment's time, method „Montonio“, and not mailed (Maria may press „Saada õpilasele“). Two taps at once make one invoice (the second finds it). It needs the seller, and only a paid payment can be invoiced. After Maria fills „Arve andmed“ the list is how earlier payments get their invoices: look at it after every setting change and after any `[invoices] … no invoice` line.
9. **The CSV for the accountant.** `GET /api/admin/arved?kuu=YYYY-MM` (this month without `kuu`; the „Arved“ page's „Laadi alla (CSV)“ for the month it shows): `;`-separated for Estonian Excel, UTF-8 with a BOM, CRLF line ends, named `MS-LAB-arved-YYYY-MM.csv`. One row for every invoice **issued** in that Tallinn month, cancelled ones included (state „Tühistatud“, sums 0,00), a refunded one's state „Tagastatud“ with its sums, paid date and way as issued (item 7): number, date, due date, buyer, buyer's company and registry code, description, sum without VAT, VAT, total, state, paid date, way. Dates are Tallinn dd.mm.yyyy; sums have a comma and no grouping. Texts are always quoted, and one a spreadsheet would read as a formula (a name starting with `=`, `+`, `-` or `@` after any white space) gets a leading apostrophe. The header words are a draft for Dim's wording sheet.
10. **The mails, and the quota.**
    - **The paid mail** (a registration's or an e-course's, section 11) carries the payment's invoice as a PDF named `MS-LAB-arve-{number}.pdf` and the line „Arve on lisatud.“ If the PDF cannot be drawn, the mail goes without both (`[invoices] {number}: the paid mail went without its PDF`).
    - **„Saada õpilasele“** sends the mail „MS LAB arve {number}“ with the PDF, the amount, the due date, the bank details and the reference, in the registration's language, to the buyer's address and, if Maria types one, to „Saada ka aadressile“ (say the student's accountant), for that send only. That second copy greets no one by name („Tere!“, «Здравствуйте!») and has no „Ava minu konto“: its reader is not the student (m9). The second address is stored only as the invoice's last-sent note (`sent_note`). It goes while Maria waits, so her screen says whether it went; a cancelled invoice is never mailed; a sample address (`@example.test`) counts as sent without a mail.
    - **Invoice mails are not counted on the daily mail quota** (`mail_quota`, the login and visitor-form caps), like the other mails that follow a real payment or Maria's own tap (the paid mail, the protocol mails): amended in the spec (D11). They count only in Resend's own 100 a day.
11. **The student's side.** On each course card of „Minu koolitused“ a quiet line per invoice, „Arve MSL2026-001 · 175,00 € · Tasutud“ or „… · Tasumata · tasu {date}“, with „Laadi alla (PDF)“; an unpaid one also shows the bank details and the reference, and „Maksa“ for exactly its amount. `GET /api/konto/arve/<id>` answers her own invoices only (the registration's or the payment's `client_id`; signing in links the registrations of her address to her), `attachment; filename="MS-LAB-arve-{number}.pdf"`, `private, no-store`, nosniff, and a 404 for anyone else's, for a cancelled invoice and for an unknown id; it is behind the coming-soon gate like every account route. An invoice that waits for its catch-up (item 7) reads „Tasutud“ on the card with no PDF link until the catch-up. A refunded one reads „Tagastatud“ (Russian «Возвращён»), its PDF as it was. A cancelled registration's unpaid invoice (or one of a session called off) stays on the card as „Tasumata“ until Maria cancels it, but with no bank details and no „Maksa“ (m8). A student who deletes her account leaves her invoices (frozen buyer): Maria sees them, nobody else does.
12. **The logs.** Ids, numbers and counts only: never a name, an address or a note; `<class>` is the error's class, code and HTTP status.
    - **Info:** `[invoices] registration N: issued <number> (invoice I)`, `invoice I: marked paid` (with `(the session is full: not confirmed)` when so), `invoice I: paid mark undone` or `receipt undone: cancelled`, `invoice I: cancelled`, `invoice I: buyer changed`, `invoice I: sent to 1 address` (or `2 addresses`), `invoice I: paid online by payment P`, `payment P: issued <number> (invoice I)` (a settlement or the catch-up made one) or `payment P: paid <number> (invoice I)` (the catch-up paid the invoice the payment was started for), `payment P: paid without an invoice (Arve andmed not filled in)`.
    - **Errors:** `[invoices] payment P: no invoice: <class>` (the savepoint: the payment is in „Arveta maksed“), `<number>: the paid mail went without its PDF`, `invoice I: the mail was not sent` and `the second address was not sent to`, and one line for each failed action or download: `registration N: the invoice failed`, `invoice I: the send failed`, `marking it paid failed`, `undoing the paid mark failed`, `the cancel failed`, `the buyer change failed`, `payment P: the catch-up failed`, `the settings save failed`, `invoice I: the admin's download failed`, `the month's CSV failed`, `the sample invoice failed`, and the student's `[invoices] I: the student's download failed: <class>`.
13. **Rollback.** A rollback of the code past this phase (section 8) leaves 0011's table and column and 0012's column and index in place: the migrations are additive and older code ignores them, so the invoices stay in the database, unseen, until the code is back. Meanwhile there are no invoice screens, no invoice routes and no invoice line on the student's cards, the paid mail has no PDF, and the numbers are not reused: the series is in the database. A payment paid meanwhile has no invoice; once the code is back it is listed in „Arveta maksed“ and Maria makes it there (if it was started for an unpaid invoice, the catch-up pays that invoice, so nothing is counted twice).
14. **Deploying** (this phase's go-live, and the order every push after it keeps):
    1. Migrations 0011 and 0012 on Railway (section 6), in one run. Railway is at 11 migrations (0010 was applied on 16.10.2026); this deploy applies 0011 and 0012, both additive, so the count goes from 11 to 13.
    2. The test plan's stamp: `node tools/testplan-stamp.mjs` from `app/`, committed with the merge (section 15).
    3. The push of `main` (Vercel deploys it).
    4. The smoke check, read-only: `/api/admin/arve/1`, `/api/admin/arved` and `/api/admin/naidisarve` answer 401 without a session, and `/admin/arved` redirects to the login.
    5. Maria fills Seaded → „Arve andmed“ (and Ettemaksu juhised, if not yet) before the first payment she wants invoiced; until then paid payments wait in „Arveta maksed“.

## 17. Contracts („Lepingud“)

Every booking has a contract: the text the student agreed to, who she is, what she bought and when she agreed, kept as a PDF by both sides (phase 4, piece 3, spec `docs/superpowers/specs/2026-10-17-contracts-design.md`, plan `docs/superpowers/plans/2026-10-17-contracts.md`; where the build departed from the spec, the spec says "amended 17.10 during the build"). It is not a digital signature and collects no personal ID code (spec D5): the contract is concluded by an explicit tick of the signed-in or registering student, logged with its time, and a PDF copy goes to her. This is not legal advice: Maria's text, and her lawyer or accountant, decide what the contract says (`docs/launch-checklist.md` section 16).

1. **What a contract is.**
   - **One contract is current per registration and per e-course access.** A contact course's group registration has a contract of kind `contact`; an e-course access has one of kind `ecourse`. An individual course's request, the waiting list, practice packages and products have none (spec D1, §8).
   - **The texts are Maria's, in Seaded.** Seaded → „Lepingud“ holds „Kontaktkoolituse leping“ (the title and the text, ET and RU; page `contract_contact`, version setting `contractContactVersion`), a placeholders hint and „Näidisleping (PDF)“. The e-course contract is the existing text, now titled „E-koolituse leping (tingimused)“ (page `course_terms`, version setting `courseTermsVersion`, with a title field of its own). Until Maria writes the contact text, the registration form shows the public „Õppetingimused“ text (page `terms`) as the contract; a registration is never blocked for want of a text.
   - **The placeholders**, exactly `{nimi}` `{e-post}` `{koolitus}` `{toimumine}` `{hind}` `{ettemaks}`, are filled at the acceptance, in one pass; an unknown `{…}` stays as typed. `{toimumine}` is the session's date (Tallinn's calendar), its city and its venue when it has one.
   - **The code:** `src/domain/contract.ts` (the rules without a database: the placeholders and how they are filled, the language, the session and payment words, the file name and the school block), `src/server/contracts.ts` (the templates, the freezing, the reads and the mails), `src/server/contract-pdf.ts` (the PDF; its text helper `src/server/pdf-text.ts` is shared with the invoice's), `src/server/contract-sample.ts` (Seaded's sample), `src/server/actions/admin-contracts.ts` (Maria's actions, `adminAction`), the routes of item 8 and the card's `ContractLine` / the forms' `ContractPreview` in `src/components`.
2. **When a contract is made.** Always in the transaction of the act that accepts it:
   - **`form`:** a group registration's submit, with the box „Olen tutvunud lepingu tingimustega ja nõustun nendega.“ ticked. The registration and its contract are one transaction under the session's lock: a contract that cannot be made rolls the registration back (the form shows its generic error, `[forms] register: not stored`), so a booking never stands without its contract. The waiting list and individual requests get none.
   - **`purchase`:** an e-course paid through Montonio. Settle's paid winner freezes the contract beside the access grant, in a **savepoint** (like the invoice step, section 16 item 7): whatever it throws, only the contract is rolled back, the payment stays paid and the course opens, and the terms gate asks her later (`terms`). Logged `[contracts] payment P: no contract` (error level). A purchase always freezes its own contract with the paid price and supersedes the access's current one, whatever its version (spec D1, amended).
   - **`terms`:** the terms gate („Olen tutvunud ja nõustun tingimustega“ + „Alusta koolitust“): a free grant („Ava ligipääs“), or a student whose accepted version is older than the current text. The same version twice makes no second contract. The gate shows the contract's title and text filled exactly as they are frozen (ruling R18). An account with no name (one Maria added by address only, „Lisa õpilane“) is asked for hers there, in a field „Nimi“: it fills `{nimi}` as she types, is frozen as the contract's student, and is saved as her account's name while that is still empty (ruling R19; `POST /api/konto/tingimused` answers 400 `{ error: "name" }` without one).
   - **`account`:** „Kinnita leping“ → „Kinnitan“ on her course card, after Maria pressed „Saada leping kinnitamiseks“ (item 5).
   - **The form sends the version of the text it showed** (the registration form, the cart's „Maksa“, the gate, „Kinnitan“): the server refuses a different or missing version with „Lepingu tekst on vahepeal muutunud — loe see uuesti ja kinnita.“ and stores nothing; the form shows the new text with the box cleared (spec D1, ruling R6). Only the version is compared: the session and the price are filled at the acceptance. A page cached before this deploy has no version field: its first submit is refused once; the page then refreshes itself with the current text, and the student ticks the box again.
3. **The frozen copy.** A contract row never changes after it is inserted, except `superseded_at` and `sent_at`. It holds the title and the text as filled (the placeholders replaced), the template's `version` and the `locale` (RU when she read the page in Russian and the Russian text exists, else ET), `fields` (the school from Seaded → „Arve andmed“, the student's name and e-mail, the course in the contract's language, the session, the price and the payment choice in words), `accepted_at`, `accepted_via` and the links `registration_id`, `access_id`, `course_id`, `client_id`, `payment_id` (each set null when its row is deleted). Later edits of the text, the course, the price or Seaded never alter an accepted contract. **Contracts outlive registrations and accounts**: cancelling or deleting a registration, or the student's deleting her account, leaves the contract with its parties frozen on it (only Maria sees it then, through the client or registration while those exist). Whose contract it is is read, never written: `coalesce(the registration's client_id, the access's client_id, the contract's own client_id)`, the live link first (spec §3, ruling R14).
4. **The snapshot.** An e-course purchase must freeze what the cart showed. The purchase's start stores that on the payment (`payments.contract_snapshot`: the version, the locale, the filled title and text, and `acceptedAt`, the moment of the press of „Maksa“), and settle copies it into the contract unchanged, with the paid price in its fields and the student as the payment names her. A text Maria saves between the cart and the payment changes nothing already frozen. A payment started before this deploy has no snapshot: it freezes no contract, and the gate asks her (`[contracts] payment P: no contract kept with it, the terms gate asks`, info).
5. **The supersede rule and the lock.**
   - **At most one current contract** per registration and per access, enforced by two partial unique indexes (`contracts_current_registration`, `contracts_current_access`, where `superseded_at` is null). A new contract for the same registration or access supersedes the current one in the same transaction (`superseded_at` set, the old PDF reads „Asendatud {date}“); the old row stays.
   - **Maria's ask:** the registration drawer's „Saada leping kinnitamiseks“ sets `registrations.contract_requested_at` and mails the link (item 6). The student's card then shows „Kinnita leping“ with the current text, and „Kinnitan“ freezes a new contract (`account`), supersedes the old one and clears the ask. It is offered on a linked, not cancelled group registration (a registration without an account says „Õpilasel pole kontot — lisa ta Õpilased lehel.“).
   - **The lock:** a contract insert takes the registration's row (`FOR UPDATE`; a contact contract) or the access's row (`completion.ts lockAccess`; an e-course contract) first, inside the caller's transaction and after its own locks, and opens no other lock, so it fits the order of section 16 item 3. The terms gate of an account with no name also writes the client's name (ruling R19): it takes the address lock (`client-auth.ts lockAddress`) before the access row, the order of settle's e-course grant and of the account's deletion, which write the client row and her access rows under that same lock. „Kinnitan“ reads Maria's ask **inside** that lock: a second tap, or a second device, finds it answered, writes nothing and answers 409. The ask and „Kinnitan“ at the same moment, in either order, leave one current contract (the ask flag is set when the ask came last), and two gate acceptances leave one contract; the unique index is only the backstop and never fires as a 500. A paid e-course purchase and the gate on the same access at the same moment meet at the access's row too (settle's grant takes it with its upsert of the access, before the purchase's contract): in either order whichever froze last is the current contract and the other is superseded, and neither deadlocks. All of it is pinned on real Postgres by `tests/e2e/contracts-race.spec.ts`.
6. **The mails** (all best effort: a failure is logged, and Maria's copy is the repair; none goes to a sample address `@example.test`, none without Resend, i.e. none in local development):
   - **The registration confirmation** carries the contract as `MS-LAB-leping-{id}.pdf` and the line „Leping on lisatud.“ It **is on the daily mail caps** (`submit.ts` sendConfirmation): at most 3 confirmations per address a day, and the day's confirmation cap of 30 (the login cap of 60 when the mail carries a login code). When a cap holds the confirmation back, the contract's PDF does not go either, and nothing is recorded as sent: Maria sees it as a contract without the line „Saadetud õpilasele“ in the registration drawer, and the repair is her „Saada koopia õpilasele“. The e-course paid mail carries the contract too; it follows a real payment and is not counted.
   - **The other contract mails** follow the student's own act or Maria's tap, so they are **not counted** on the daily mail quota, like the invoice mails (section 16 item 10).
   - **„MS LAB leping“** (the terms gate, „Kinnitan“ and Maria's „Saada koopia õpilasele“): „Kinnitasid lepingu {date}.“, the contract's title with its course and session, „Leping on lisatud.“ with the PDF, and a button „Ava minu konto“ (none for a student without an account). No login in it. `contracts.sent_at` is recorded once Resend took a mail that carried the PDF.
   - **„MS LAB leping kinnitamiseks“** (Maria's ask): a short greeting, one line saying Maria asks her to confirm the contract for the course, and a plain link to her account page in her language (`/konto`, `/ru/konto`): no token, no code (spec D4, ruling R9).
   - **The copy never goes without its PDF** (ruling R15): „Saada koopia õpilasele“ draws the PDF first and refuses with „Lepingu PDF-i ei õnnestunud koostada — proovi uuesti.“ when it cannot. The automatic mails go without the PDF and without „Leping on lisatud.“ when it fails to draw.
7. **The PDF.** A4 portrait, white, Jost, the logo; several pages when the text is long. Drawn on **every download from the frozen row** (no file is stored; the same row gives the same bytes), in the contract's language: the title, „Pooled“ (the school and the student), „Koolitus“ (the course, the session, the price, the payment), the text, and „Kinnitatud elektrooniliselt {date time}, {name} ({e-mail})“ with the way. Until Maria fills „Arve andmed“ the school block says "MS LAB" and prints no more than she typed. pdf-lib is loaded only when a PDF is drawn. `next.config.ts` traces `./assets/fonts/**` into every function that can draw a contract: the account API, `/api/payments/**` and `/api/cron/**`, `/admin/**`, `/api/admin/leping/**`, `/api/admin/naidisleping/**` and the public course page (`"/*/koolitused/**"`, where the registration form's action mails the PDF). A bracketed key traces nothing under Turbopack; a function log saying `ENOENT … assets/fonts` means a key missed one.
8. **The routes and screens.**
   - **Maria:** the registration drawer's block „Leping“ (the current contract, the superseded ones, „Laadi alla (PDF)“, „Saada koopia õpilasele“, „Saada leping kinnitamiseks“); the client drawer's „Lepingud“ (the student's contracts, replacing the old list of terms acceptances); Seaded → „Lepingud“. `GET /api/admin/leping/<id>` (any contract's PDF) and `POST /api/admin/naidisleping` (the sample, a form POST of the texts on the screen, up to 40 000 characters each; stored nowhere) are behind `withAdmin`; the buttons are server actions (`adminAction`).
   - **The student:** `GET /api/konto/leping/<id>` (her own contract's PDF: `attachment; filename="MS-LAB-leping-{id}.pdf"`, a 404 for anyone else's, 10 downloads an hour), `GET /api/konto/leping-tekst/<registrationId>` (the text „Kinnita leping“ shows, only while Maria's ask is open on her own registration) and `POST /api/konto/leping` („Kinnitan“); the gate's `POST /api/konto/tingimused` freezes the e-course contract. Every PDF answer is `private, no-store` with `x-content-type-options: nosniff`.
9. **The logs.** Ids and counts only, never a name, an address or a text; `<class>` is the error's class, code and HTTP status. `grep '\[contracts\]'` finds them all.
   - **Info:** `[contracts] contract C: mailed: true|false`, `contract C: not mailed (sample address)`, `registration N: the ask was mailed: true|false`, `registration N: the ask was not mailed (sample address)`, `payment P: no contract kept with it, the terms gate asks`; and, from the forms, `[forms] register: the contract's text changed since the page was loaded: nothing stored` and `[forms] ecourse: the contract's text changed since the cart was loaded: nothing started` (a refused version, item 2).
   - **Errors:** `[contracts] payment P: no contract` (the savepoint of item 2: read it and tell the student to open the course; the gate asks her), `contract C: the mail went without its PDF`, `contract C: mailed, but the send was not recorded`, `contract C: the mail failed`, `registration N: the ask's mail failed`, and one line for each failed action or download: `the texts' save failed`, `registration N: the ask failed`, `contract C: the copy's PDF could not be drawn`, `contract C: the copy failed`, `contract C: the admin's download failed`, `the sample contract failed`, and the student's `[contracts] C: the student's download failed` (the id without the word „contract“, as its siblings `[invoices] I: …` and `[certificate] N: …` in `account-api.ts`).
10. **Rollback.** Migration `0013_contracts` is additive: the table `contracts` with its indexes and foreign keys, `payments.contract_snapshot` and `registrations.contract_requested_at`. Older code ignores all three, so a rollback of the code (section 8) leaves the contracts in the database, unseen, until the code is back. Meanwhile the forms show their old box and freeze nothing, there is no contract screen, route or card line, the terms gate stores only its version, and a payment paid meanwhile has no contract (its student is asked at the gate). **Every e-course buyer since the deploy is asked again at the old gate**: a purchase now writes its contract and no `terms_acceptances` row, and the old gate reads only that table. That is harmless (she ticks the box once more, and the old gate stores its version). Nothing needs undoing. The one thing a rollback cannot take back is a mail already sent with a contract.
11. **Deploying** (the order every push of this phase keeps):
    1. **Migration 0013 on Railway** (section 6). Railway is at 13 migrations (0012 was the last); this deploy applies 0013, additive, so the count in `drizzle.__drizzle_migrations` goes from **13 to 14**.
    2. The test plan's stamp: `node tools/testplan-stamp.mjs` from `app/`, committed with the merge (section 15).
    3. The push of `main` (Vercel deploys it).
    4. **The smoke checks**, read-only, from a machine with no session:
       - `GET /api/admin/leping/1` and `POST /api/admin/naidisleping` answer **401** without an admin session.
       - `GET /api/konto/leping/1`, `GET /api/konto/leping-tekst/1` and `POST /api/konto/leping` give no access without a student session. While the coming-soon gate is on (`SITE_GATE`, section 2) a script gets the gate's **404** `{ ok: false, error: "not_found" }`, and a browser the coming-soon page; once the gate is off they answer **401** `{ ok: false, reason: "none" }`.
       - `/admin/seaded` (signed in as Maria) shows the card „Lepingud“ with „Näidisleping (PDF)“, and the sample starts with `%PDF`.
    5. **Real mail delivery**, done by the controller on staging into Dim's own mailbox, with `+proov<n>` addresses (the tester's own address with `+proov<n>` before the @, section 15 item 6; never a sample address, which is never mailed). One registration with an account, then: (1) the **registration confirmation** with `MS-LAB-leping-{id}.pdf` attached; (2) Maria's „Saada leping kinnitamiseks“ → the mail **„MS LAB leping kinnitamiseks“** with a plain link to the account; (3) Maria's „Saada koopia õpilasele“ → the mail **„MS LAB leping“** with the PDF; (4) the student's „Kinnitan“ → the mail **„MS LAB leping“** after it. Open the PDF in each, on the phone too, and read the log for `[contracts]` errors afterwards.
    6. Maria writes „Kontaktkoolituse leping“ in Seaded before the first real registration she wants a contract for (until then the form shows the public „Õppetingimused“ text), and reads „E-koolituse leping (tingimused)“ (`docs/launch-checklist.md` section 16).

## 18. Reviews („Arvustused“)

Graduates' own words under each course and on the home page, shown only with the student's permission and Maria's approval (phase 4, piece 4, spec `docs/superpowers/specs/2026-10-18-reviews-design.md`, plan `docs/superpowers/plans/2026-10-18-reviews.md`; where the build departed from the spec, the spec says "amended 18.10 during the build"). The line under the blocks, „Tagasiside on MS LAB-i koolituse läbinud õpilastelt. Avaldame selle õpilase loal ja pärast kontrolli.“, is the site's statement of how reviews are checked; it is not legal advice, and Maria's privacy text says the rest (`docs/launch-checklist.md` section 17).

1. **What a review is, and where it comes from.** One table, `reviews` (migration 0014). A review is one of two kinds:
   - **`student`:** a copy of a graduate's answer to „Kas soovitaksid seda koolitust ka teistele? Miks?“ and of the name she chose, made by the feedback form's submit **in the same transaction** as the feedback, when she ticks „Luban seda vastust avaldada MS LAB kodulehel — selle koolituse lehel ja avalehel.“ (`server/course-feedback.ts submitFeedback`). The tick can be set only while that answer has text, and it needs a name („Nimi, mida näidatakse“, prefilled with her first name and the initial of her last, e.g. „Kati K.“, at most 40 characters); the server refuses a tick without text (`consentText`) or without a name (`consentName`) with a 400 and writes nothing. The text and the name are copies made at consent: nothing updates them, not a later change of her name in Minu andmed and not Maria. **An answer given before this deploy has no permission and never becomes a review.**
   - **`manual`:** a review Maria adds in „Tagasiside“ → „Arvustused“ → „Lisa arvustus“ (a past student's paper form or message): the course, the shown name, the text, the date written (from the year 2000 on), its language and a required internal note „Kust see pärit on?“ (up to 500 characters, never shown publicly). A new one is published when she first adds it. She can edit and delete these, and only these; an edit keeps its status and its „Avalehel“ setting, and a review moved to another course refreshes both courses' pages. Whether the student allowed it is Maria's responsibility: the site cannot check it.
   - **Who may offer one.** The feedback form opens as before for a contact course (section 12 item 6) and, new, for an e-course once its access is „Lõpetatud“ (`course_access.completed_at` is set) and not revoked (an access that ended by its date still counts: she finished the course). The questions are Maria's paper form, unchanged, for both. An e-course's feedback row has `course_feedback.access_id` set and `registration_id` empty (a check requires exactly one of the two). Maria's approval is the check that the writer took part: each student review in „Arvustused“ shows the registration's status and whether a protocol was sent, or „Lõpetatud {date}“ for an e-course.
   - **Maria's notice.** The existing „Uus tagasiside: …“ mail and Telegram message gain the line „Lubab avaldada — vaata „Tagasiside“ lehel.“ when the student ticked. No new mail is sent.
   - **The code:** `src/domain/review.ts` (the limits, the name offered, the consent and the manual form's rules; the only place the limits are written), `src/server/reviews.ts` (the withdrawal, Maria's decisions and manual reviews, the admin's list and the two public reads), `src/server/course-feedback.ts` (the form's state and its submit), `src/server/actions/admin-reviews.ts` (Maria's actions, all `adminAction`), `ReviewsPanel` and `ManualReviewForm` in `src/components/admin`, `ReviewList` and `ReviewMore` in `src/components/site`, and the card's `ReviewLine` in `src/components/account`.
2. **The statuses.**
   - **`pending` „Ootab kinnitust“** is where a student review starts; **`published` „Avaldatud“** and **`hidden` „Peidetud“** are Maria's two answers. „Avalda“ and „Peida“ work from any status (a press on a hidden review publishes it, as the button says; the same press twice is harmless) and set `decided_at`. A student's review is never edited: Maria changes only `status`, `featured` and `decided_at`.
   - **„Avalehel“ (`featured`)** is a toggle on a published review only; it also shows the review on the home page. Hiding a review keeps its `featured` value, so publishing it again brings it back to the home page: a hidden review that still has it carries an „Avalehel“ tag, and a quiet line under the status line says „Avalehel näidatakse kuni 6 uusimat.“ (`HOME_REVIEWS_MAX`), because Maria can mark a seventh and only the newest six show.
   - **The screen** is a tab of „Tagasiside“: `/admin/tagasiside?vaade=arvustused`, with `&olek=ootel|avaldatud|peidetud` for one status. „Kõik“ lists by status (waiting, published, hidden) and then newest written. There is no paging: tens of rows are expected, and the status filter is enough until it passes about 100. The page heading shows „Arvustusi ootab kinnitust: N“ on both tabs, and the count opens the waiting ones. A review of a draft course says „(mustand)“ after the course's name (the mark the „Lisa arvustus“ course list carries): it shows nowhere until the course is published. After „Avalda“ or „Peida“ the focus stays on the row; in a status-filtered view the row leaves the list on the refresh, and the focus goes to the next row (else the one before it, else the status line).
   - **A press on a review that is gone** (the student took her permission back meanwhile) answers „Seda arvustust enam pole — õpilane võttis loa tagasi.“ and the row goes.
3. **What the public pages show.** Only `published` reviews of a `published` course; unpublish a course and its reviews leave every page (the home page too), and come back with it.
   - **The course page:** the block „Õpilaste tagasiside“ after the course's content and before the trainer's card: the newest six, then „Näita kõiki (n)“ for the rest, up to 50. The button opens the rest in place, with no request; reviews 7 to 50 are in the page's data and not in its HTML until it is pressed (the site is noindex until the launch).
   - **The home page:** the section „Õpilaste kogemused“ after the trainer section: published reviews marked „Avalehel“, newest first, at most six, each naming its course as a link.
   - **Both:** a block with nothing to show is not drawn (no heading, no notice). A review is shown as written, in its own language, on the Estonian and the Russian page alike (its words and name carry `lang` where that is not the page's); the headings, the notice and the month follow the page's language. Each shows the words, the name, the month and year, and no score, no stars and no average. There is no structured data for reviews.
4. **The cache.** Every review change calls `revalidatePublic({ kind: "reviews", course: <slug> })` (`server/cache-targets.ts`), which expires that course's page in both languages and the home page; the next request renders them again. Maria's actions call it before they answer, so does the student's withdrawal, and an account deletion calls it after its commit for each course that had a review of hers. Both pages also have `revalidate = 300`, so anything that does not call it (a row deleted by hand in the database, a registration or a course deleted there, which takes its reviews with it) shows for at most 5 minutes. A failed call is logged (item 7) and never undoes the change; the pages then catch up on their own.
5. **The withdrawal and the account deletion.**
   - **„Võta luba tagasi“:** while her review exists, her card of the course (a contact course's registration, an individual course's registration with no session, or an e-course) shows „Lubasid oma soovitust avaldada“ with the button, whatever Maria has done with the review (she is not told). `POST /api/konto/arvustus/tagasi` `{ reviewId }` deletes the review at once, its row locked `FOR UPDATE` (her answers stay with Maria), refreshes the pages, and answers 200 `{ ok: true }`; 404 `{ error: "review" }` when it is not hers, was added by Maria, or is gone already; 429 after 30 presses in an hour, a limit of its own (`client-review-withdraw`) apart from the feedback form's 10 an hour for the answers and the „Ei soovi“s, so that taking permission back is not refused because she answered and dismissed forms first.
   - **Deleting her account** (Minu andmed → „Kustuta konto“) already deleted her feedback, and her reviews go with it (the foreign key `reviews.feedback_id` cascades). The slugs of their courses are read first, so each course's pages and the home page are refreshed once the deletion is committed. Her registrations stay with Maria (section 12). A review also goes when its registration, its access or its course is deleted.
6. **The locks.** A submit reads the registration or the access `FOR SHARE`, writes the feedback row with `INSERT … ON CONFLICT DO NOTHING` and then `UPDATE … WHERE submitted_at IS NULL`, and inserts the review, all in one transaction: two submits at the same moment (a double tap, two devices) leave one answer and one review, the second answered 409 `sent`, never a 500. The withdrawal and Maria's „Avalda“, „Peida“, „Avalehel“ and edits take the review's row `FOR UPDATE` first: withdrawn first, her press finds the review gone; her press first, the withdrawal then deletes what she published. The account deletion takes the address, then the registrations, then the accesses (section 12 item 4), which a submit's `FOR SHARE` meets. All of it is pinned on real Postgres by `tests/e2e/reviews-race.spec.ts` (the unit tests' single connection cannot show it); the whole path, from the tick to the withdrawal, is `tests/e2e/reviews.spec.ts`.
7. **The logs.** Ids only, never a name, a text or an address; `<class>` is the error's class, code and HTTP status. `grep '\[reviews\]'` and `grep '\[feedback\]'` find them.
   - **Info:** `[feedback] registration N: submitted` (or `access N`), `[reviews] review R: pending (registration N)` (or `access N`: a ticked answer became a review), `[reviews] review R: published`, `hidden`, `featured`, `unfeatured` (Maria's presses), `added`, `edited`, `deleted` (her own reviews), `withdrawn` (the student's), and `[feedback] registration N: Maria notified by e-mail: true|false, Telegram: true|false` (or `access N`).
   - **Errors:** `[reviews] review R: the decision failed: <class>`, `review R: the home page toggle failed`, `review R: the save failed` (or, for a new one, `[reviews] a new review's save failed`), `review R: the deletion failed`; `[account] revalidating the reviews failed: <class>` (a withdrawal or an account deletion; the pages catch up within 5 minutes); `[public-cache] revalidating <path> failed` (Maria's action); `[account] feedback rate limited` (the form's 429) and `[account] review withdrawal rate limited` (the withdrawal's 429, item 5).

## 19. Newsletter campaigns („Uudiskirjad“)

Maria writes a campaign in the admin („Uudiskiri“ → „Kampaaniad“: the texts in Estonian and, if she wants, in Russian, a picture, a code and a button, with a live preview of the real mail) and sends it to every subscriber as **one ordinary mail each**, from the same sender as the site's other mails: `RESEND_API_KEY`, `MAIL_FROM` on `send.mslab.ee`, Maria as the reply-to. **Nothing is set up in Resend and nothing is kept there**: no contacts, no lists, no second key. The site's database is the only list and the record of consent. The design is `docs/superpowers/specs/2026-10-20-newsletter-simple-design.md` (Dim, 20.10: "everything in this project needs to be very simple and usable"; it replaces the sending half of the 18.10 spec `2026-10-18-newsletter-campaigns-design.md`, whose editor, preview, mail look, recipients and welcome mail stand), the plan `docs/superpowers/plans/2026-10-20-newsletter-simple.md`. The home page's popup is another thing (`campaign`, „Hüpikaken“); the newsletter's own names are `newsletter_campaigns`, `newsletter_deliveries` and `domain/newsletter-campaign.ts`.

1. **How a campaign goes out.**
   - **Who gets it.** Every **confirmed** `subscribers` row at the moment of the press, once per address; never a sample address (`@example.test`, the demo data's and the live checks'). Each gets her own mail in her language (the Estonian text under her Russian footer when the Russian subject or text is empty; the editor says so first), with **her own** unsubscribe link, `${SITE_URL}/api/newsletter/loobu?t=<her token>` (`SITE_URL`, never a request's address: the mail is kept long after), and the headers `List-Unsubscribe` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, which make the mail program's own unsubscribe button (Gmail's „Tühista tellimus“) work: its POST to that address answers 200 and removes her row. The token in the address is the whole capability, so that POST is judged by its body (`List-Unsubscribe=One-Click`, or no body at all with the token in the address) and not by its Content-Type or its `Origin` header: a mail provider's server, or a web mail client's browser, may send either, and the button's own cross-site check does not apply to it. A subscriber who unsubscribes before her turn is skipped; someone who signs up after the press is not added and gets the next campaign.
   - **The press.** „Saada kõigile“ asks „Saadad kampaania {n} tellijale (eesti keeles {a}, vene keeles {b}). Kas saadame?“ with the counts as they are now (a press is refused, with a note to reload the page, if the counts or the campaign changed since the question). On „Saada“ the site writes **one `newsletter_deliveries` row for each recipient** (status `waiting`, her address, language and token as they are then) in one transaction, makes the campaign `sending` ("going out over the coming days"), and sends the **first batch at once**: the page waits for it (`/admin/uudiskiri` sets `maxDuration = 120`; the batch has 60 s, and its mails go 0.6 s apart because Resend answers 429 above about two requests a second, so the day's 70 about fit). What does not fit the day's room waits for the next day's **daily job** (item 3), a batch a day until no row waits; then the campaign is `sent`. If the press's own time runs out while the day still has room, the rest waits for the next day too. With 13 subscribers a campaign takes one day.
   - **What Maria sees.** While it goes out: „Saadetud {sent} / {n} — ülejäänud {left} lähevad järgmisel päeval.“ next to „Peata saatmine“ (item 5), in the list too (the tag „Saatmine pooleli“). Done: „Saadetud {date} · {n} tellijale“, with a line for the addresses that failed and one for the mails with no answer, if there were any. The page reads the progress when it loads and after her actions; it does not refresh itself, so a batch the daily job ran shows after a reload.
   - **„Saada proov“** is one ordinary mail, now, to Maria's address (`MARIA_EMAIL`) or the signed-in admin's, in either language; the subject starts „[Proov]“, at most 10 an hour, counted like every mail. Its unsubscribe link and `List-Unsubscribe` header go to the site's test page (`/api/newsletter/loobu?proov=1`: „Proovikiri — päris kirjas viib see link loobumisele.“), which changes nothing. It works for any campaign, sent or not.
2. **The day's counter and the room of 70.** One counter, the row `<UTC day>:all` of `mail_quota`, counts every mail the site sends in a UTC day (the day Resend's own limit uses): logins, confirmations, protocols, invoices, contracts, Maria's notices, welcome mails and campaign mails; each mail Resend accepts adds one, best effort (the sweep, section 5, deletes counters older than 7 days). A campaign sends only while the counter is **below 70** (`CAMPAIGN_DAILY_ROOM`, `domain/newsletter-campaign.ts`) of the free plan's 100 a day, and stops there: 30 are left for the day's other mails. The site's own mails are never stopped by the campaign's counter, and the per-kind caps (logins, forms) are as before. A busy day (the site's mails alone passed 70) sends no campaign mail that day, which is fine. A mail whose answer never came (`unknown`) is not counted, so the 70 is soft by those few; Resend's own 100 is the hard stop (item 4). 70 a day at most for campaigns, plus the site's own, stays within the plan's 3,000 a month. UTC midnight is 02:00 or 03:00 in Estonia: the room fills again then.
   - **Is the 30 of headroom enough?** Today, yes. At a few hundred subscribers, no longer on every day: the daily job (04:00 UTC, 06:00 or 07:00 in Tallinn) sends its 70 early in the Estonian day, so the whole day's logins, confirmations, Maria's notices, protocols and invoices share the 30 that are left, while their per-kind caps would let 85 or more through, and a campaign that drives registrations costs two mails each (the confirmation and Maria's notice). About 10 such registrations plus the evening's login codes can use the 30 up, and Resend then refuses the site's own mails, **login codes among them, until the next UTC day** (02:00 or 03:00 in Estonia). The remedies are to send a big campaign when no course-registration rush is expected, or a paid Resend plan (Dim's decision; none is bought today). Nothing in the code changes. When the list passes about 100, look at `<day>:all` on campaign days (`select day, sent from mail_quota where day like '%:all' order by day desc limit 7`), and lower `newsletter_daily_room` (item 7) if the site's own mails after a batch come near 30.
3. **The daily job `GET /api/cron/uudiskiri`, at 04:00 UTC** (`app/vercel.json`, an hour after the sweep; Hobby's exact minute within the hour varies, so it runs some time between 04:00 and 04:59). Vercel sends `Authorization: Bearer <CRON_SECRET>`; with no `CRON_SECRET` set, or any other header, it answers 401 and does nothing. It first turns the claims older than 6 minutes into `unknown` (item 4), then gives the **one** campaign going out (the oldest) a batch, while the day's counter is below 70 and its time lasts (270 s of `maxDuration = 300`; 300 s on Hobby needs Fluid Compute: verify it at the go-live, section 9). The answer is JSON: `{ ok: true, campaignId: null }` when nothing is going out; after a batch `{ ok: true, campaignId, stopped, total, sent, waiting, failed, unknown, skipped }`, where `stopped` says why rows still wait (`room`: the day is full or Resend's limit; `refused`; `time`) or is `null`; `{ ok: false }` with 500 when the database fails. Its links are `SITE_URL`'s whatever address the request came to. It is open through the coming-soon gate (`SITE_GATE`, section 2).
   - **Running it by hand** (the automatic run is once a day, and Dim's checks need it at once): in Vercel open the project → **Settings → Cron Jobs** and press **„Run“** beside `/api/cron/uudiskiri`; Vercel sends the secret itself. Only the production deployment has crons. If there is no „Run“: `curl -H "Authorization: Bearer <CRON_SECRET from the project's variables>" https://mslab.ee/api/cron/uudiskiri` answers 200 with `ok: true`; a 401 is a wrong secret. The secret goes in the shell only.
4. **The outcome map: each mail goes at most once.** A row is **claimed** before its send (`FOR UPDATE SKIP LOCKED`, committed first), so two runners (the press, the daily job, a second tab) never take the same row, and its outcome is written only while it is still claimed. Every outcome is exactly one status:

   | What happened | The row | The batch |
   | --- | --- | --- |
   | Resend accepts the mail | `sent` | goes on |
   | Resend refuses **this address** itself (a validation error that names the `to` field) | `failed`, never sent again; Maria sees „Kiri ei läinud {n} aadressile: aadress ei sobinud.“ | goes on |
   | No answer that says: a timeout (8 s), a 5xx, the network, a crash | `unknown`, **never sent again by itself**; „{n} kirja kohta pole teada, kas see läks. Neid ei saadeta uuesti.“ | goes on; **three in a row stop it** as refused (Resend is down: the rest waits instead of all turning `unknown`) |
   | A claim older than 6 minutes (a runner that died after claiming; every batch and the daily job sweep for it; a slow runner whose answer comes later finds its row no longer claimed and writes nothing) | `unknown`, never `waiting` again: the mail may have gone | – |
   | Resend's **daily or monthly limit** is reached (a 429 that names the quota) | back to `waiting`: nothing was sent | **stops** (`room`); the next day's job continues |
   | Any **other refusal**: the key (`invalid_api_key`, `restricted_api_key`, `missing_api_key`), the domain not verified or the account in testing mode, another field, the rate limit still there after its one retry, `RESEND_API_KEY` not set | back to `waiting` | **stops** (`refused`); Maria sees **„Saatmine peatus: Resend keeldus. Kirjuta Dimile.“** (a mark in `kv_entries`, `newsletter:refused:<campaign id>`, which goes with the campaign's next accepted mail) |
   | The subscriber is gone before her turn | `skipped` | goes on |

   A 429 that only says "too fast" is tried once more after a second, never a third time. Bounces that arrive later are Resend's business; the site does not track them, and the row stays `sent`.
   - **When Resend refuses** (the „Resend keeldus“ line): the runtime log has `[notify] Resend rejected the e-mail: <class>` (the error's name and HTTP status, never its message). An `invalid_api_key` or `restricted_api_key`: fix `RESEND_API_KEY` in Vercel and redeploy. A domain or testing-mode error: Resend → Domains (`send.mslab.ee` verified, the account out of testing mode). The rows are still `waiting`: run the daily job by hand (item 3) or let the next one do it; Maria cannot press again, because the campaign is `sending`.
   - **An `unknown` row** is the one thing that may need a person: if it matters, look in Resend → Emails for that recipient and time, and if the mail is not there, send that one subscriber her mail by hand. The site never does it by itself.
5. **„Peata saatmine“** (Draft). While a campaign is going out, Maria can stop it. She is asked „Kas peatan saatmise? Veel saatmata {n} kirja ei lähe välja. Seda ei saa tagasi võtta.“; on „Jah, peata“ every waiting row becomes `skipped` and the campaign is `sent` with the counts of the mails that went („Saadetud {date} · {n} tellijale“). A row claimed at that moment is finished by the batch that holds it, and nothing more is claimed (the stop and every claim take the campaign's row, the stop for update and a claim for share, so they cannot cross); if Resend then refuses that one mail, its row is `skipped` like the rest, never put back to `waiting` under a campaign that is `sent`. A typo noticed after the press, or a key problem, never leaves a campaign hanging. A stopped campaign is not continued; „Kopeeri“ makes a new draft.
6. **One campaign at a time.** While one campaign is `sending`, „Saada kõigile“ on another says „Eelmine kampaania on veel pooleli — see läheb välja, kui eelmine on saadetud.“ (Draft) and sends nothing; Maria can still write, save, copy and test. Every press first takes a transaction lock (`newsletter-press`), so two presses at the same moment (two tabs, two campaigns) go one after the other and the second finds the first `sending`; `tests/e2e/newsletter-race.spec.ts` pins the lock on real Postgres (item 13).
7. **The lowered room for a check: the settings key `newsletter_daily_room`.** Optional, and absent in normal life: Dim uses it to see a campaign continue the next day without having 70 subscribers. The row `newsletter_daily_room` of `settings` is a JSON number from 1 to 70 (a fraction is cut, below 1 is 1, above 70 is 70) and is read by every batch **only when it is there**. It is the **most mails one campaign sends in a UTC day**, on top of the 70 rule; it can only lower the room, never raise it, and Maria's pages know nothing of it. With the URL in the shell only (section 6):
   - set: `insert into settings (key, value) values ('newsletter_daily_room', '2') on conflict (key) do update set value = excluded.value`
   - **delete it afterwards, always, also when the check is broken off:** `delete from settings where key = 'newsletter_daily_room'`. A row left behind caps every later campaign without a word on Maria's screen.
   - **A present key logs `[newsletter] room override N` on every batch** (item 8), so a forgotten one shows in the runtime log; a value that is no number is ignored, with `[newsletter] the setting newsletter_daily_room is no number: ignored` (never the value).
   - With the room at 2 and three subscribers the press sends two and Maria sees „Saadetud 2 / 3 …“; the daily job sends nothing more while the row is there (today's two are used up: `stopped: "room"`); once the row is deleted the job sends the third. The test plan's checks „Kampaania, mis ei mahu päeva, jätkub järgmisel päeval“ and „Peata saatmine“ are this, and the e2e does the same on test addresses.
8. **The logs.** Ids and counts only, never an address, a token or a text; `<class>` is the error's class, code and HTTP status (never a message). In Vercel: the project → Logs; `grep '\[newsletter\]'` finds the campaigns, `[cron] uudiskiri` the daily job, `[notify]` the mails themselves.
   - **Info:** `[newsletter] campaign N created`, `campaign N copied from campaign M`; `campaign N: pressed, K deliveries written (et A, ru B)` (or `not pressed (busy|changed|sent|empty|notFound)`); `K stale claims marked unknown (campaign N)`; `room override N` (item 7); `campaign N: batch: S sent, F failed, U unknown, K skipped; L of T left` (with `, stopped (room|refused|time)` when rows still wait; one line for each batch, the press's and the daily job's); `campaign N: sent, K mails went (et A, ru B)` (done); `delivery D: no longer claimed, its outcome (sent|…) not written` (a slow runner's answer came after the 6-minute sweep had marked its row `unknown`: the row stays `unknown`); `campaign N: stopped, K waiting deliveries skipped`; `campaign N: stopped meanwhile, delivery D skipped instead of waiting` (a refusal that came after the stop); `one-click unsubscribe: subscriber N` (the row's id, never the token) or `one-click unsubscribe: no subscriber for the token` (a used or a made-up token; still answered 200); `campaign N: a test sent (et|ru)`, `campaign N: the test did not go (address|quota|refused|unknown)`, `campaign N: a test refused, 10 this hour already`. The daily job: `[cron] uudiskiri: no campaign is going out`, or `[cron] uudiskiri: campaign N: S sent of T, W waiting, F failed, U unknown, K skipped` (with `; stopped (room|refused|time)`). The mails: `[notify] Resend accepted the e-mail: <id>` for each, `[notify] Resend asks for fewer requests: the e-mail is tried once more`.
   - **Warnings and errors:** `[newsletter] the setting newsletter_daily_room is no number: ignored`; `[notify] Resend rejected the e-mail: <class>` and `[notify] Resend request failed: <class>`; `[newsletter] campaign N: delivery D: the send failed: <class>` (the row is `unknown`); `campaign N: the refusal mark unavailable|not written|not removed: <class>`; `campaign N: the save|copy|send's preparation|send|stop|test failed: <class>` (a server action failed and the page said so), `a new campaign's save failed: <class>`, `the campaign preview failed: <class>`; `unsubscribe failed|one-click unsubscribe failed|unsubscribe page: language unavailable: <class>`; `[newsletter] unsubscribe POST: a token in the address and a body that is neither the button's nor one-click's; nothing deleted` (a mail program that sent a body this route does not read: look at what it sends); `[cron] uudiskiri failed: <class>`.

12. **Things to know.**
    - A campaign is a mail of the site, not something kept in Resend: its dashboard shows each as an ordinary sent e-mail (Emails), there is nothing to set up or clean up there, and an address Resend blocked after a bounce fails for the next campaigns too, as it does for the site's other mails. Unsubscribing happens on the site only (the mail's link, the mail program's button, or „Minu andmed“).
    - Links in a campaign to the site's pages land on the coming-soon page until the public launch; the logo (`/brand/logo.png`), pictures (`/media/…`) and the unsubscribe link (`/api/newsletter/loobu`) go through the gate. A picture must be one of the site's uploads. While `SITE_GATE` is on, the confirmation of „Saada kõigile“ and the result of „Saada proov“ carry one line (Draft): „Koduleht pole veel avatud — kirja lingid ja nupp viivad „Tulekul“ lehele.“ It is a notice and not a block: a „we open soon“ campaign is a legitimate one. The page reads the setting the way the middleware does.

3. **The course draft rules, in plain words** (rulings R-a to R-e of the plan; the texts are in `adminEt`):
   - **A published course is edited in a draft.** Every change to its cards is saved by itself (1.5 s after the last key, or when she leaves the field) into a draft, and the public page and the students keep seeing the live course. The draft has the parts of the editor: the basics („Õppevorm“, level, address, language, title, summary, text), the price (an e-course's price, access, videos and next discount, or a contact course's group and individual price and duration), „Õpiväljundid“, „Koolitus sisaldab“, the protocol points, the test, the certificate's skills and volume, the gallery, the recommendations, the badge, and the **order, names and short texts of the course's modules and lessons**. A change typed back to what is live drops its draft.
   - **„Avalda muudatused“** puts the drafts live in one go and refreshes the public course pages once.
